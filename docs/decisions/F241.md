# F241 A release's fuzz run may be made of two runs, the later one running only the targets whose corpus reaches what changed (2026-11-11)

**Kind:** Record
**Status:** Active
**Area:** repository
**Held by:** fuzz.release-two-runs

*Sits beside F210 (the fuzz run may run on GitHub Actions) and F239 (a
release's cross-check made of runs at one seed), and holds for the fuzz
run what F239 holds for the cross-check.*

**Built.** `tools/fuzz-release.sh` ends a full run with the coverage map
(`out/fuzz-map.txt`; `tools/fuzz-release.sh map CORPUS` makes it from a
joined run's corpus, as the last job of `.github/workflows/fuzz.yml` does)
and runs a later run with `FARADAY_FUZZ_EARLIER` (the targets
`tools/fuzz-plan.py` names) or `FARADAY_FUZZ_TARGETS` (a list); the
workflow takes a `targets` input; `tools/fuzz-join.py --later` joins the
two records and corpora. The map holds the files each target's corpus
reaches, the crate each compiles in and the compiled-in files with no
code; a changed constant is followed to the files that name it by its
name alone, and a changed entry of the strings table (`name: "text",`) by
its field name alone: a target reruns when its corpus reaches a file that
uses that string, never for the wording alone. The map is made from one
instrumented build of every target, each target's corpus replayed and
exported as many at once as the machine has cores.

**Why.** The run before a release fuzzes 73 targets for 600 seconds each.
When a change after a passed run touches one parser, running every
target again checks nothing new for most of them. On GitHub the whole run
takes about 24 minutes, nine and a half of them compiling, and nineteen
runners; on one computer it is an hour or more. Which targets a change can
alter was measured three ways on 2026-11-11, at 0.2.0's tree and over
0.2.0's published corpus:

- **The files compiled into a target** (cargo's dep-info for its binary).
  A target compiles in every crate its fuzz crate depends on, not only
  the ones it calls: 175 of the repository's files for each target of
  `fuzz/`, about 718 for each of `faraday/fuzz/`, and the strings file in
  all 73. The change that made the Bitcoin Core wallet reader refuse a
  large range (one reader file and one string) reran all 73 this way, 37
  for the reader's file alone. Of the 505 commits since 0.1.9 that touch
  a file compiled into a target, the median reran 37 and 252 reran all 73.
- **The files each target's corpus reaches** (an instrumented build,
  `cargo fuzz coverage`, over the corpus the run left, read with
  `llvm-cov`). A target reaches few files: a median of 4, at most 170
  (`app_scanned`, which reads every kind of scanned payload). Of the 721
  files compiled in, 285 are reached by some target. The wallet reader's
  file is reached by four targets (`core_wallet_records`,
  `classify_file`, `inbox_found`, `app_scanned`), and the string it
  changed is named by a file three targets reach, five in all. Over the
  same 505 commits, the median reran 3 to 6 targets, and about one in
  eight still reran all 73, most of them for a change to a fuzz crate's
  manifest or lock. Running the 73 instrumented targets over the
  corpus took about two minutes one after another, after an instrumented
  build about as long as the fuzz build itself; the map of reached files
  is about 40 KB.
- **A list of parser files and their targets, kept by hand and held by a
  lint.** It says no more than the second way and has to be kept in step.

The second way is chosen. It holds because of what the corpus is: the
corpus a run exports keeps, minimized, an input for every edge the run
covered, so the files it reaches are the files that run reached. A target
whose corpus never entered a changed file ran the same code, on
everything it tried, as it would now, and its earlier result stands for
the new tree.

**Decision** (owner, 2026-11-10: a release's fuzz run made of two runs,
only the targets a change reaches run again).

1. **A release's fuzz run is one run or a combination of two.** The later
   run takes the earlier run's record, its corpus and its map of reached
   files, and runs only the targets the change reaches, for the same time
   a target, each from its own corpus in the earlier run's export. Every
   other target's result is the earlier run's. A combination of more than
   two runs is not made: a third run is against the combination's tree
   again, as a fresh earlier run.
2. **The map is made at the end of a full run** (a run of every target,
   whole or joined from parts), from that run's own exported corpus and
   that commit's code: for each target, the repository's files in which
   its corpus executes code. It is written beside the record and names
   the record's commit; the later run refuses a map of another commit.
3. **What a change reaches** is read from the files that differ between
   the earlier run's commit and the later one:
   - a changed file that a target's corpus reaches reruns that target;
   - a changed constant or static, or a file with no code of its own (a
     table, the strings), counts as a change to every file that names
     what changed, so the targets reaching any of those files rerun;
   - a change that cannot be followed to files, every target whose
     binary compiles the file in reruns: a build script, a file included
     as bytes, a crate's manifest;
   - a change to a fuzz crate's manifest, lock or toolchain, or to the
     tools that run the fuzzing, reruns every target;
   - a target added, or its source, seeds or dictionary changed, runs.
   A target that did not pass in the earlier run runs again.
4. **The record names both runs.** The combination writes one record and
   one corpus, as `tools/fuzz-join.py` does for the parts of a run. The
   record gives each run's date, commit, starting corpus and the targets
   it ran, and for each target which run its row is from. The release
   notes quote it as they quote a full run's. Everything else in F210
   stands: it may run on GitHub Actions under the same limits.

The rule is not airtight in one way: a target's earlier run stands for
code it never entered, and a longer run might have entered it. That holds
equally for the earlier run itself, which the release would have shipped
on.
