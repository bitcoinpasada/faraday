# F189 The vault is an age file: one passphrase, scrypt, TOML inside, five sizes, the smallest a QR code (2026-11-02)

**Kind:** Record
**Status:** Amended by F190, F217
**Area:** security
**Held by:** review

*Amended by F217 (2026-11-05): point 6's QR vault is a third form of a seed, a codex32 string or a passphrase on the backup board, a seed's only copy as one is opened to test before the lock, and the Starter does not scan or print one (`docs/BACKUP-FLOW.md` §17.25).*

*Amended by F190 (2026-11-02): a file vault is a KDBX 4 database under Argon2id and a QR vault an RFC 9580 OpenPGP message under Argon2id; points 1, 3, 5, the QR file of 6, 7, 9 and 10's reader are replaced; points 2, 4, what a QR vault holds and does in 6, and 8 are kept (`docs/VAULT.md`).*

*Amends F158 (2026-11-02): point 4, the four-slot container, is replaced by this decision. Amends F159 (2026-11-02): points 1, 3 and 7; points 2 and 4 are kept as point 7 below says. Amends F160 (2026-11-02): the vault's container is no longer a construction of Faraday's own; the F79 area `vault` checks it against Go `age`, which Faraday's authors did not write.*

**Why.** The vault was Faraday's own container: four equal slots under
Argon2id and XChaCha20-Poly1305, read by nothing outside Faraday but
`tools/vault/open.py`, which Faraday's authors wrote. It was first in
line for an outside review (F158 point 4), and a person holding a vault
could not open it with any other program. A seed backed up as a code
needed a format of its own beside it (KEF, age or another), and the
smallest vault, 262,357 bytes, could not be one. Decoys need no second
slot: a BIP-39 passphrase or another derivation path gives one inside a
wallet's own standards. No vault exists anywhere (owner, as F159 found),
so nothing is migrated.

age v1 (C2SP, age-encryption.org/v1) is a published specification with
a reference implementation outside Faraday (Go `age`), a second outside
implementation (`rage`) and published test vectors (the age testkit). Its
passphrase files are scrypt (RFC 7914), HKDF-SHA-256 (RFC 5869),
HMAC-SHA-256 (RFC 2104) and ChaCha20-Poly1305 (RFC 8439), all already in
Faraday. Its header MAC is keyed by the file key, so a file opens to one
content only, whichever passphrase opens it: what F159 point 3's
commitment block was for.

**Decision** (owner, 2026-11-02; `docs/VAULT.md`).

1. **A vault is an age v1 file with one scrypt stanza**, read and
   written as the age specification says. Faraday writes `.age`, binary,
   never armored. A file is a vault by its contents (the age version
   line and one scrypt stanza), whatever its name. An age file whose
   stanza is not scrypt, or with more than one stanza, is named ("An age
   file for a key, not a passphrase") and not opened. One passphrase per
   vault; there are no slots.
2. **The passphrase is put in Unicode NFC**, as F159 point 2 says, and
   its UTF-8 bytes are scrypt's password.
3. **Memory: five steps**, scrypt's work factor N = 2^16 to 2^20, r = 8,
   p = 1: 64 MiB, 128 MiB, **256 MiB (the default)**, 512 MiB and 1 GiB.
   A machine is offered the steps it can open; a vault meant for a Pi
   Zero 2 W takes 64 or 128 MiB. A reader refuses a work factor above
   2^20 before it allocates anything. The work factor is in the clear
   header, so the memory a vault needs is shown before its passphrase is
   asked for. Each step adds ≈ log2(2N) bits to every passphrase (the
   1 KiB block steps of one guess, as `docs/VAULT.md` §3.1 counts
   Argon2id's): ≈17 to ≈21. Faraday's own scrypt
   (`core/faraday-crypto/src/scrypt.rs`, F178: it wipes its working
   memory) does the work, on the worker (F184).
4. **Five sizes.** **QR**, for one item, and four file sizes, **64 KiB,
   256 KiB (the default), 1 MiB and 4 MiB**, the size of the contents
   before encryption. The contents are padded to the size, so a file's
   length says only which size it is.
5. **Inside: TOML v1.0.0**, each item in its published text form: a
   seed as its BIP-39 words, a wallet as its BIP-388 policy or
   descriptor, an entry with an `otpauth://` URI, Secure Boot keys and
   certificates as PEM (RFC 7468), a GPG key as its armored OpenPGP
   secret key (the form `gpg --export-secret-keys` writes unprotected), a
   passphrase, a codex32 share or a note as its text, the seal count with
   a TOML date and time. The padding is blank lines at the end. `age -d`
   gives a file a text editor shows. Which TOML names mean what is
   Faraday's own rule, in `docs/VAULT.md` §7, and fails closed: a file
   edited by hand and encrypted again with `age` opens when every item
   reads; an unknown name, a malformed value, or a GPG key not of
   Faraday's own shape (an Ed25519 key with one Ed25519 signing subkey,
   unprotected) refuses the file, as an unknown record does today.
6. **The QR size** holds one item, a note, or nothing yet: a seed's
   words (12 or 24; a Seed XOR part is 24), a codex32 share, a BIP-39
   passphrase with the fingerprint of the key it belongs to, or text
   the person types (owner, 2026-11-02). No item longer than a 24-word
   seed. Its contents are the item's keys at the top of a TOML document,
   named as the file vault's are (`words`; `codex32` and `for`;
   `passphrase` and `for`; `note`) and written one to a line, padded to
   the one length every QR vault has, 226 bytes, so a code does not show
   what it holds: the age file is 408 bytes, QR version 15 (77 × 77) at
   medium error correction. It is a vault like the others: it unlocks
   with its passphrase, is listed on Vaults while open, marked as a QR
   vault, and shows what it holds. **What it holds can be changed at any
   time** (owner, 2026-11-02), however it was made: a key put in, the
   text typed or edited, up to the form's maximum. Each change is sealed
   as a new code; a code printed before still opens to what it held
   then. **QR is a size in Create a vault**, made empty, and the backup
   flow, wherever a seed, a share or a passphrase is placed, makes one
   holding it; several shares or parts take **one shared passphrase**
   or **a passphrase for each**, and the flow says to keep each in a
   separate place. A QR vault is not a secret under `docs/QR.md` §7.1:
   it is drawn and printed as any code is, and its page and the backup
   flow offer it as a labelled PNG and as its `.age` file to the Outbox
   (owner, 2026-11-02), the label never saying what it holds. Scanned
   wherever a SeedQR is taken, it asks for its passphrase, opens, and its
   words go to the seed sheet (**Use without a passphrase** / **Add a
   passphrase**, `docs/FLOWS.md`), then load as a scanned SeedQR's
   do. The Starter scans and prints a QR vault and never asks for its
   passphrase.
7. **What F159 keeps.** The seal count (F159 point 4) is a line inside
   the TOML, and an older copy is still named at unlock. Every seal is a
   new age file: a new salt, a new file key and so a new scrypt run, as
   the specification requires ("A new salt MUST be generated for each
   stanza and each file"). A copy can therefore no longer be told from
   another vault without opening it: a backup plan's `seals` line names
   another vault by an identifier inside it, not by its salt, and a copy
   is named older when it is opened, not while it sits unopened in
   Files. F159 point 1 (`.fvlt`, `FVLT`) and point 3 (the commitment
   block) are replaced by points 1 and the header MAC above; point 7's
   outside review of the container is no longer needed, since the
   container is no longer Faraday's own.
8. **Every seal's random bytes are the session's** (owner): the salt
   (16 bytes), the file key (16) and the payload nonce (16) are one
   `fresh_bytes("vault seal", 48)`, two answers (F154), so whatever the
   person added through Add randomness is mixed in
   (`docs/OWN-RANDOMNESS.md` §2.3). Create a vault (a QR vault included) and the
   backup flow offer **Add randomness** before the vault is made. A seal waits for
   the answers it needs and never stretches fewer.
9. **Written here, the passphrase part of age only** (F178: only the
   part used is written; the established Rust implementation brings
   every other recipient type, post-quantum and public-key, and
   localisation with it): the header, the scrypt stanza, the header MAC
   and the payload in 64 KiB chunks, over Faraday's scrypt, HMAC and
   HKDF and the `chacha20poly1305` crate. Checked against the age
   testkit's scrypt and header vectors, and in the F79 area `vault`
   against Go `age` both ways: each opens the files the other made.
10. **FVLT is removed.** Nothing reads a `.fvlt` file. The vectors,
    samples and fuzz seeds are made again as age files;
   `tools/vault/open.py` becomes a reader of the TOML that `age -d`
   gives.

**Not done.** scrypt's second half reads memory at places the passphrase
decides, a cache-timing side channel on the computer that unlocks; it is
later work under the Security scope, as wiping freed copies is.

**Amends** F158 (point 4, the four-slot container), F159 (points 1, 3
and 7: the name, the commitment block and the container's outside
review) and F160 (the vault among Faraday's own constructions).
