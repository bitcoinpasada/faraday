# F333 Settings' Mode is a segmented button in its card, and a press on another asks first in one sheet (2026-11-24)

**Kind:** Record
**Status:** Active
**Area:** design
**Held by:** tests

*Amends F81: its Settings Mode row, which opened the mode sheet, is the modes as a segmented button in Mode's card on a window wide enough for the card; on the small panel the row stays. Material 3's segmented button (https://m3.material.io/components/segmented-buttons/guidelines) takes two to five segments; a mode that cannot be chosen would be its disabled segment (F81's dimmed label); the app offers no mode it cannot choose today.*

**Why.** Every setting's choices show with no press to see them (`docs/WORKSPACE.md` §9), and a mode change is a lock that empties the session, which a press on a row did without asking when nothing was held.

**Decision** (owner, 2026-11-24).

1. The modes are inline in Mode's card as a segmented button, the one in use chosen, a segment for each mode the app offers (the sheet lists the same).
2. A press on another mode asks first, in one sheet: "Change to Testnet?" (worded by the mode pressed), **Not now** and **Lock and use Testnet**. It is the lock's own sheet (LockAsk), so it lists what is kept and what leaves memory as any lock does, and nothing when the session holds nothing; where the lock refuses or asks more (an unsaved key, a vault changed, a file waiting) it is the same sheet, never a second one.
3. A press on the mode in use does nothing. The pill's sheet is unchanged: a mode chosen there closes it and the change sheet asks once.
4. A mode change is still a lock: what is refused, what leaves memory and what is kept do not change (`docs/MODES.md` §2, point 6).
