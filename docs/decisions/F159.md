# F159 The vault is a `.fvlt` file beginning `FVLT`, its passphrase in NFC, each slot committed to its key and counting its seals, and its construction told in Learn (2026-10-28)

**Kind:** Record
**Status:** Active
**Area:** security
**Held by:** review

**Why.** The vault's format left four things open. A passphrase typed in
another Unicode form ("é" as one character or two) derived another key.
XChaCha20-Poly1305 does not commit to its key, so a slot can be made
that opens under two passphrases with other contents under each. An
older copy of a vault opens as if current, and nothing shows it. The
file's name, `.ofv`, and its magic, `OFVT`, predate Faraday's name. And
no place tells a person, in one readable account, how the vault is built
and what it does and does not promise. No vault exists anywhere: Faraday
has no users yet (owner), as F144 found for the other formats.

**Decision** (owner, 2026-10-28; `docs/VAULT-HARDENING.md`. NFC alone
and the visit's rule for a newer copy were settled by the coordinator
the same day under the owner's word, for the owner's review; the seal
counts in the plan and recognition by contents are the owner's, 23:45
and 23:40 EDT: the spec's §11).

1. **The name and the magic.** A vault file ends in `.fvlt` and begins
   `FVLT` (`46 56 4c 54`); the version byte after it stays 1. `.fvlt`
   matches the magic and no other use of it was found; `.fv` is taken
   by HEASARC's fv scripts (Debian's `ftools-fv`) and Fresh View's
   caches. A file named `.ofv`, or beginning `OFVT`, is not read. A file
   the person selects is a vault by its contents, the magic and one of
   the four vault sizes, whatever its name or extension (owner, 23:40
   EDT): a copy named `VAULT~1.FVL`, or with no extension, opens. `.fvlt`
   is what Faraday writes and what its lists group by.
2. **The passphrase is put in Unicode NFC** before Argon2id, at
   creation and at opening, in `faraday-vault`, and nothing else is done
   to it. Two passphrases with one NFC form are the same passphrase.
   RFC 8265's OpaqueString in full (its space mapping and refused code
   points) is not done; the spec's §12 says what it would add and cost.
3. **Each slot is committed to its key**: its plaintext starts with 32
   zero bytes, required back as zeros (Albertini, Duong, Gueron, Kölbl,
   Luykx and Schmieg's padding fix, USENIX Security 2022). A slot whose
   tag verifies and whose block is not zero refuses the file. *L* and
   the file sizes do not change.
4. **Each slot counts its seals**: a record of type 16 holds how many
   times the slot was written and when. Unlock shows it. An older copy
   is named when a newer one was opened, sealed or sits among the copies
   in Files since power-on; a stick visit holds no key and reads no
   counts, since a process that holds a key is never handed a stick. A backup
   plan records each other vault it places by salt, size, slot position,
   count and the slot's digest (owner, 23:45 EDT), so an older copy is
   named across a power-off from an open vault's plan; never refused.
   What it cannot detect is stated with it: a rollback when no newer
   copy is seen since power-on and no open plan records one, and a vault
   rolled back with its own plan.
5. **No fallback, no migration, no version change**: nothing reads the
   format before this one.
6. **The construction is told in Learn.** The manifest gains
   `[[construction]]` (`docs/CRYPTO-LEARN.md` §18, schema 2): an account
   of a format that several actions share, drawn after a Learn page's
   own sections and on /cryptography before its actions' blocks, its
   numbers and names read from the code and held by `check.py`. The
   vault's account and passphrase strength are the first two. A sentence
   about work not built reads "Planned, not built" until it lands.
7. **An outside review** of the container follows the build, scoped by
   the spec's §10.

**Assumes.** The fresh nonce for every seal, built separately
(`docs/OWN-RANDOMNESS.md`, F154).

**Amends.** F148: the manifest carries constructions beside actions.
