# F160 A check counts only against code Faraday did not write; Faraday's own constructions are labelled until an outside review; Bitcoin Core in the cross-check (2026-10-29)

**Kind:** Record
**Status:** Active
**Area:** crypto
**Held by:** crypto.independence-labelled, crypto.independence-said

**Why.** STANDARDS §0 said that where no other implementation exists, "a
reference written separately from the spec's text, never from Faraday's
code, counts". A review of the cross-check (2026-10-29) found that about
half its areas compare Faraday's Rust with Python models Faraday's own
authors wrote: BIP-32 in `btc.py`, the PSBT reader, the signer and
finalizer, BIP-137 and BIP-322, the vault's container, own randomness,
the entropy procedures and the Demo roller. A model written by the same
authors from the same text catches a slip between two transcriptions.
It does not catch a misreading both share, or a flaw in a spec Faraday
wrote itself, so calling it independent overstated the check. Faraday's
own constructions can have no outside implementation at all.

**Decision** (owner, 2026-10-29). It replaces STANDARDS §0's sentence
on own formats and procedures, and amends F79.

1. **What counts.** A check is independent only against an
   implementation Faraday did not write, pinned and used as published,
   or against the other program end to end (Bitcoin Core, `gpg`,
   `openssl`). A model written by Faraday's authors, or by an agent
   working for them, is Faraday's own, whether written from the spec or
   from the code, and is said to be Faraday's own wherever the check is
   described.
2. **One source for the labels.** Each action with a cross-check area
   states, in `docs/crypto/actions.toml`, its reference's
   `independence`: its `class`, `outside` (code Faraday did not
   write), `own-over-outside` (Faraday's own model over outside code,
   naming the part Faraday wrote in `ours`) or `own-only`, and its
   `author`. The app's and the website's Cryptography blocks,
   STANDARDS §2 to §5 and §7 and the cross-check's README are generated
   from it, and `docs/crypto/verified.py` fails an action with an area
   and no class (`schema = 3`).
3. **Faraday's own constructions.** Where no outside implementation can
   exist (the vault's container, own randomness, cards, the camera's
   commitment, a mix, Faraday Demo's roller, the in-memory seal, the
   Secure Boot generator), the construction carries the label "own
   construction, not yet independently reviewed" (the action's `label`)
   until an outside review. The vault and own randomness stay in the app
   under that label; the others stay as F158 has them. An outside party's
   model, written from the spec alone, or a named outside party's
   reproduction of the published vectors, counts as that review; who
   reviews is the owner's call. A decision records a review, and the
   label goes with it.
4. **Bitcoin Core is required for the cross-check.** The official
   release, pinned and checked against its signatures, outside the tree;
   the cross-check's network namespace has loopback for Core's RPC and no
   other network (`docs/CROSSCHECK.md` §10.4).
5. **Pinning.** btclib, embit and HWI are vendored by commit and SHA-256,
   as python-mnemonic is; python-ecdsa and PyCA `cryptography` come from
   the distribution's signed packages.
6. **Other toolchains.** Go is allowed for LND's aezeed and its AEZ.
   BIP-322 is checked against outside code where a reasonable
   implementation exists; where none does, BIP-322 is held out of the
   app until it can be checked, never labelled self-checked.
7. **Lineage.** libsecp256k1, under rust-secp256k1 and Bitcoin Core and
   written by the authors of Core's test framework's `key.py` and the
   BIPs' reference code, is accepted as shared; so is miniscript, whose
   implementations come from one group. btclib and python-ecdsa are the
   second lineage for the curve.
8. **Faraday's own models are retired** once outside code replaces
   them.
