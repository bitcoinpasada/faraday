# F208 A file vault takes a key file, and a KeePassXC file protected by a YubiKey opens from that key's typed secret (2026-11-04)

**Kind:** Record
**Status:** Active
**Area:** security
**Held by:** keys.vault-components

*Amends F190 (2026-11-04): point 1's composite key may hold a key file, and point 2's message changes, since a file that needs a key file or a YubiKey can now be opened here.*

*Not built. `docs/VAULT.md`'s Open line says what is left.*

**Why.** F190 let a KeePass file open under its passphrase alone. KDBX 4
records nothing that shows a key file or a challenge-response key, so
such a file looked like a wrong passphrase and could not be opened. A key
file is KeePass's published second component and costs a parser and a
hash. A YubiKey's challenge-response is KeePassXC's: the key computes
HMAC-SHA-1 under a 20-byte secret, people write that secret down when
they program the key, and a person who has lost the key has no other way
in. The computation needs no hardware once the secret is typed.

What was read, in KeePass 2.60's `KcpKeyFile.cs` and `KcpKeyFile.Xml.cs`,
KeePassXC 2.7.12's and 2.8.0's `src/keys/` and pykeepass 4.2.0's
`kdbx_parsing/common.py`:

- **The challenge is the KDF's seed**, the Argon2 salt `S`, not the master
  seed (`CompositeKey::transform`), which KeePassXC draws anew at each
  save. It is padded to 64 bytes in the manner of PKCS#7
  (`YubiKeyInterfaceUSB::performChallenge`). A key programmed with
  `hmac-lt64`, which `ykman` always sets (yubikey-manager 5.7.2,
  `yubikit/yubiotp.py`) and KeePassXC's own guide uses, takes the last
  byte and every equal byte before it as padding (`ykpersonalize.1`), so
  it computes over `S` alone, less any `0x20` that `S` ends in.
- **The response joins after the other components, hashed once more:**
  `SHA-256(SHA-256(passphrase) || key file's key || SHA-256(response))`,
  all of it before Argon2 (`CompositeKey::rawKey`).
- **The three readers of key files agree on the order** (XML, 32 bytes,
  64 hexadecimal characters, otherwise the file's SHA-256) and differ at
  the edges. An XML key that is not 32 bytes: KeePass uses it as it is,
  KeePassXC fits it to 32. A version 2 file with no hash: KeePass takes
  it, KeePassXC and pykeepass do not. A `KeyFile` document with no key:
  KeePass refuses it, the other two hash the file. An empty file:
  KeePass hashes it, KeePassXC refuses it.

**Decision** (owner, 2026-11-03: both parts, no YubiKey hardware support;
`docs/VAULT.md` §1.1, §3.2, §4, §5, §7.1 and §8 are how it reads).

1. **The composite key** is the SHA-256 of the components present, in
   that order, as above. Without a key file or a secret it is F190's.
2. **A key file** is read as `docs/VAULT.md` §3.2 says, and where the
   three readers differ Faraday refuses, naming the file. That is the
   stricter rule, so no key file means one thing here and another in a
   KeePass app.
3. **At unlock**, a file vault's page offers **Add a key file** (a file
   chosen from Files, where it came in through the Inbox; its copy there
   is wiped once the vault opens) and
   **Add a YubiKey secret**, each optional. Nothing in the file says which
   it needs, and nothing is written to say so: `PublicCustomData` could,
   but it would tell anyone holding the file. Neither the choice nor the
   file's name is remembered.
4. **What is held.** Of a key file only its 32-byte key is kept, in
   `faraday-keys`, beside the passphrase in the vault's slot; the file's
   bytes are wiped as soon as the key is made from them. The secret is
   held the same way. Both wipe as they drop, are never shown back and
   have no reveal. A key file Faraday makes leaves through a named reveal
   of its own (`docs/KEYS.md`).
5. **A seal asks for nothing.** It needs what the vault was opened with,
   and has it, so a lock and an idle lock seal as they do now. A seal
   never leaves out a component on its own: the file it writes needs what
   the copy opened needed, until the person changes that (point 7).
6. **A seal after a recovery still opens with the YubiKey.** A seal draws
   a new salt (F190 point 8), so it needs the response for a salt the key
   has never seen; that is why the secret is held. Faraday computes it,
   and KeePassXC with the key, or a second key holding the secret, then
   computes the same. A vault with a secret never writes a salt ending in
   `0x20`, whose last byte is changed to `0x21` when one is drawn: no
   seal then rests on the padding rule, which nothing here can run on a
   real key. Reading a file KeePassXC saved does rest on it, for one file
   in 256.
7. **Faraday never sets a YubiKey up.** A secret is taken only to open a
   file, and a vault opened without one cannot be given one. A vault opened
   with one offers **Remove YubiKey secret** on its ⋮, taking effect at the
   next seal (owner, 2026-11-04): someone who lost the key would otherwise
   type the secret every time, and KeePassXC cannot drop the requirement
   without the key. A key file
   can be offered, added, replaced and removed on Faraday's own vaults
   (Create, and **Key file** on the vault's ⋮), taking effect at the next
   seal; the screens say that losing it locks the vault, and that it is
   worth little kept beside the vault's file. A vault made in a backup
   flow or for the KeePass export has the passphrase alone until then.
   A QR vault has neither: OpenPGP has no such component.
8. **The secret** is 40 hexadecimal digits, either case, with spaces and
   colons between them ignored, since tools print it in those forms.
   Anything else is refused before Argon2 runs, saying how many digits
   were typed. It cannot be checked otherwise, so a wrong digit reads as
   wrong credentials.
9. **The wrong-passphrase message** names what was tried, and without a
   component says the file may need one (`docs/VAULT.md` §4). It can never
   say which was wrong: the header's HMAC fails alike for each.
10. **A passphrase is still required** (owner, 2026-11-04). The refusal of a file with an
    empty passphrase (`docs/VAULT.md` §7.1) stays, so a file protected by
    a key file or a YubiKey alone is not opened.
11. **A key programmed for fixed 64-byte input is not covered** (owner,
    2026-11-04). It would
    compute over all 64 bytes. No file or reference shows what one
    returns, and trying it would cost a second Argon2id at each failure.
    Such a file reads as wrong credentials.
12. **Written here, only the part used** (F178): the key file reader, over
    the vault's XML reader, and the challenge, over the vetted `hmac` and
    `sha1` crates the vault already uses. A key file is taken in from
    outside, so its reader has a fuzz target. KeePassXC's construction is
    a convention other programs follow (`keepass` 0.17.0 implements it),
    not a specification of Faraday's, so F177's label does not apply.

**What the checks can and cannot prove.** Key files are checked both ways
against pykeepass and `keepassxc-cli`. The challenge-response is checked
against a file KeePassXC ships for its own tests
(`tests/data/YubiKeyProtectedPasswords.kdbx`, with the secret its
`TestCli.cpp` publishes), and in both directions against `keepassxc-cli`
through a stand-in for the key behind the PC/SC interface, so that
KeePassXC's own padding, composite key and salt handling are what is
judged. `keepass` judges the format only, as F193 says, with its local
challenge. The stand-in's HMAC and padding rule are Faraday's reading of
Yubico's documents: no check here shows that a physical YubiKey opens a
file Faraday sealed.

**Amends** F190 (points 1 and 2).
