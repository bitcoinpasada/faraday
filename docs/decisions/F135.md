# F135 A script of several keys is signed only for a registered wallet (2026-10-27)

**Kind:** Record
**Status:** Active
**Area:** wallets

**Why.** A multisig, miniscript or taproot-tree input names its
cosigners only through the PSBT, which is the coordinator's word. The
first audit's finding on multisig change was fixed by verifying change
only against a registered wallet; an input of several keys was still
signed whatever keys the coordinator put beside this device's, so a
compromised coordinator could have this device sign a spend from a
wallet the person never set up (its other keys the attacker's). Ledger
signs only for a registered wallet policy and Coldcard refuses a PSBT
that matches no registered wallet unless told to trust it.

**Decision** (owner, 2026-10-27, for this release;
`core/faraday-psbt/README.md`, `docs/WALLETS.md` §3.3, `docs/FLOWS.md`
Spend tab):

1. **The rule.** An input that is not final, names a loaded key in its
   key origins, and spends a script of more than one key (a `multi` or
   `sortedmulti` of two or more in P2SH, P2WSH or P2SH-P2WSH; a P2WSH or
   P2SH-P2WSH miniscript naming two or more keys, a `pkh` hash counting
   as a key unless the input states its key; a taproot script path that
   carries leaves which, with its internal key, name two or more
   distinct keys between them, any of which does not read as a
   miniscript, or which are not the output's whole tree: the control
   blocks agree on one internal key and root, that key tweaked by that
   root is the output, and every hash beside a leaf is a carried leaf or
   a node built from them, so a leaf left out counts as several keys.
   The internal key counts unless it is BIP 341's unspendable point, the
   one unspendable key a PSBT can show to be one. A taproot input that
   carries no leaf spends by its key path, one key, whatever root it
   states, and is not held) is signed
   only when a registered wallet (one in the session: from a vault, a
   wallet file or code, Create, or the register sheet below) gives
   exactly its script at the chain and index its key origins state.
   Every registered wallet and every origin is tried, and a wallet
   whose script it is answers, so two wallets that share a key (two
   multisigs on one BIP-48 account) are told apart. Otherwise the PSBT is
   **Blocked**, `WarningKind::WalletNotRegistered`: "input {i} spends
   from a wallet of several keys that is not registered here; register
   the wallet to sign". No override signs it. Single-key inputs
   (BIP 44, 49, 84, 86), a taproot key path, and MuSig2 (registered
   already) are unchanged; an input naming no loaded key is not signed
   here either way and does not hold the spend up.
2. **Register from the PSBT.** Where the only blocks are that one, and
   the PSBT carries BIP 174's global xpubs, the inspection offers the
   wallet the PSBT defines (`faraday_psbt::Registration`) when every
   blocked input is a `multi` of one wrapper, threshold and count of
   keys, every key of them states its origin, exactly one global xpub
   has that origin less its chain and index, and the keys are sorted in
   every input (`sortedmulti`) or in one order of cosigners in every
   input (`multi`). A key whose origin is the master itself, with no
   account, is not offered. Anything else is not offered: miniscript and
   taproot wallets come by their descriptor. Where the keys are sorted
   at every address the spend uses and in one order of cosigners, both
   readings are tried against every input and every output that names
   the wallet's chains: the one that gives them all is offered; where
   both do, the sheet offers the choice, **Sorted** first ("Most
   coordinators sort the keys") or **In this order**.
3. **The sheet.** The Spend review shows **Register this wallet**
   under the blocked line, or, where nothing is offered, "Load this
   wallet's descriptor to sign". The sheet (DESIGN §4.13's dialog)
   shows the shape ("2 of 3, P2WSH, sorted"), each cosigner's
   fingerprint and path with "Yours" where a loaded key derives that
   cosigner's key, a name (the PSBT's file name at first) and **Hold to
   register** (DESIGN §4.13). The hold writes the descriptor, and adds
   it only once it gives the script of every input of its shape at the
   chain and index the input states and of every output whose key
   origins name one of its chains, and only once one of its cosigners is
   the person's and every cosigner under a loaded fingerprint is: the
   cosigner's extended key is the one the loaded key gives at that
   cosigner's path, worked out from the key itself
   (`faraday_psbt::register`). A mismatch stays on the sheet by name
   ("These keys do not give input 0's address", "Output 1 names this
   wallet but is not its address", "None of these keys is yours", "Key
   {fingerprint} at {path} has your fingerprint but is not your key"):
   whoever wrote the PSBT could otherwise write a key of theirs under
   the person's fingerprint, and a wallet of nobody's keys here would
   vouch for their outputs as change. The
   wallet is then added as a wallet file is (`Session::add_policy`: the
   same refusals, kept for the session, offered to a vault as any
   loaded wallet), and the spend is inspected again and can be signed.
4. **A wallet holds a key** (`Context::holds`) when one of its keys is
   under a loaded fingerprint and is that key's own extended key at its
   path (an account's, or one the session works out once from the key
   for the wallet's path and keeps), and no key of it under a loaded
   fingerprint is another key. A key of the person's is "Yours" only
   where the loaded key itself gives it; a wallet's word for a key under
   the person's fingerprint is never taken. Whatever way a wallet came
   in, one that holds no
   loaded key verifies no change and lets no input of several keys be
   signed: a watch-only multisig whose keys are all cosigners' now
   counts its change as unverified, as it would with no wallet loaded.
5. **Paths are bounded.** A key origin of more than sixteen steps is
   refused, in a PSBT (`Psbt::parse_bytes`), in a wallet's keys
   (`WalletPolicy`) and by `Keys::xpub_at`, never cut: no wallet
   standard goes past six steps, and each derivation from an origin
   stays one bounded piece of work
   (`faraday_bip::keys::MAX_PATH_STEPS`).
6. **The cross-check** (F79) counts the refusal as a known difference
   where BIP-174's signer signs, only where Faraday's refusal names
   `WalletNotRegistered`; its reference builds a registered wallet's
   script (`multi`, miniscript, and `tr()` through Core's
   `taproot_construct`) and asks that the wallet hold a held key, as
   Faraday does; and its corpus registers the wallet of half its
   `multi` and miniscript inputs so their signatures are still
   compared.
