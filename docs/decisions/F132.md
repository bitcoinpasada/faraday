# F132 A tr() wallet states who can spend by the key path (2026-10-26)

**Kind:** Record
**Status:** Active
**Area:** wallets

**Why.** A `tr()` wallet with a script tree can also be spent by its
internal key alone, without the tree. A wallet whose internal key is BIP
341's NUMS point and one whose internal key is some other key read the
same as "2 of 3" from their leaves, while only the first needs two of
the three signatures. Wallets with a key path are legitimate (a primary
key on the key path, a timelocked tree under it), and an unspendable
key other than the bare NUMS point cannot be told from a key someone
holds, so refusing them is wrong.

**Decision** (owner, 2026-10-26: warn loudly, never refuse; WALLETS
§3.4, DESIGN §5 Wallets, FLOWS Wallets tab). Every `tr()` wallet with a
script tree states who can spend by the key path, worked out once when
its descriptor is read and kept on the policy (`KeyPath` in
`core/faraday-bip/src/policy.rs`):

1. **Nobody**: the internal key is the NUMS point, or an extended key
   whose public key is the NUMS point (every child of it is the NUMS
   point plus a tweak anyone can work out). "Key path: none
   (unspendable)". A one-leaf `multi_a` or `sortedmulti_a` over every
   key of the wallet reads as its quorum, "2 of 3".
2. **A key of the wallet**: the internal key is one of the wallet's
   extended keys with its origin. "Key path: <the key> alone". The
   wallet is never shown as a bare "k of n": it is a tree whose key
   path is its first way to spend.
3. **Any other key**: a plain key that is not the NUMS point, or an
   extended key with no origin over another point. The danger line, "A
   key that is not one of this wallet's keys can spend everything
   alone, without the other signatures: <the key in groups of four>".
   No "k of n" is shown for the wallet. The wallet is added only after
   a hold on a sheet that names it and the key ("Hold to add this
   wallet", DESIGN §4.13's confirmation for an act that can lose
   everything), whichever way it came in; Cancel, or a press beside
   the sheet, adds nothing. The hold runs the press that asked again,
   so the flow that asked (Files, Restore, a family, a vault) goes on
   as if nothing had been asked; once held, the same wallet is not
   asked about again in that session. The wallet's card keeps the
   danger line; its signatures here are counted against its one leaf's
   own quorum ("1 of 2 signatures here" for a 2-of-3 leaf), and where
   a "Can spend" would show, the card, the list, the Wallets page's rows
   and the sidebar read "Another key can spend" in the error tone. A
   spend from it repeats the danger line as a caution at the head of
   the transaction's warnings.

A `sortedmulti_a` leaf reads as a quorum only when it holds every key
of the wallet, the same count `multi_a` is held to. A key with no
origin is read only as the internal key over the NUMS point; anywhere
else, a leaf's key included, it is refused as BIP-388 refuses it.
