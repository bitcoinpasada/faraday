# F181 Memory work follows the security model: no wiping allocator, no batch for copies the lock already bounds, none for Faraday Demo and the Starter (2026-10-31)

**Kind:** Record
**Status:** Active
**Area:** crypto
**Held by:** speed.no-wiping-allocator

**Why.** A review of the tree on 2026-10-31 (`docs/ESTABLISHED.md`
§4.8, §4.9) found copies of secrets left in freed heap, and that
`core/faraday-crypto/src/wipe.rs`'s `WipeOnFree`, which wipes every
freed block, is installed in no shipped program. Installed,
it writes every freed byte and moves every growing buffer, on every
allocation, so its cost falls on drawing, the camera and the Starter's
writes, most on the Pi. What it adds is a wipe of copies in freed heap
before the process ends. Faraday runs on an offline computer that is
powered off after use, `docs/SECURITY-MODEL.md` leaves cold-boot attacks
on RAM out of what it defends against, and on the stick and the Pi the
kernel's `init_on_free=1` and the app's restart at every lock already
bound such a copy.

**Decision** (owner, 2026-10-31).

1. No shipped program installs `WipeOnFree` or any other global
   allocator. The website's build never does.
2. The secrets that matter are wiped where Faraday's own types hold
   them (faraday-keys' types, `SecretText`, `Zeroizing`). The other
   copies in freed heap the review found are not chased one by one: on
   the stick and the Pi the restart at every lock bounds them
   (ESTABLISHED §4.8, not a batch); a manifest line or module doc that
   claims more than the code does is corrected (§7.8).
3. Faraday Demo and the Starter run on an online computer, and everyone
   using them knows it: no memory or timing work is done for them alone, and
   what Transfer reads is saved as it is today.
4. What wiping does not reach is said as stated limits (ESTABLISHED
   §4.9), in `docs/KEYS.md` and the manifest's Secret handling (§7.9).
5. Installing it in any program is a new decision, made with numbers:
   that program's late-flow timings with and without it
   (`docs/SPEED.md` §7), its peak memory, the full test suite run with
   it installed, the allocator run under Miri, and a fuzz target that
   grows and shrinks buffers through it.
6. `wipe.rs` stays in `faraday-crypto`, with its tests.
