# F229 A Bitcoin Core descriptor wallet's wallet.dat is read, never written, and its records checked again, through a SQLite reader of Faraday's own (2026-11-09)

**Kind:** Record
**Status:** Active, built: the SQLite reader, the wallet reader, the cross-check against Bitcoin Core and the Read a Bitcoin Core wallet tool
**Area:** wallets
**Held by:** review

**Why.** A person moving a Bitcoin Core wallet to cold storage, or
keeping one offline as a backup, has the file `wallet.dat` and no other
form of it. Faraday can say what the file holds and whether it is whole
without Bitcoin Core: its descriptors, which are active, its network,
and whether each private key is the one its public key says. Since
version 23 Bitcoin Core makes descriptor wallets, kept in a SQLite
database. The record layout is Bitcoin Core's own, published in its
source and used by that project alone; SQLite's file format is
published by SQLite; the descriptors are BIP 380 to 386. STANDARDS §0
takes one project's format only by a decision.

**Decision** (owner, 2026-11-05: read only, never edited or exported;
2026-11-09: Faraday's own SQLite reader, and a wallet's private keys
checked and wiped, never loaded).

- **A descriptor wallet's `wallet.dat` enters under STANDARDS §0 by this
  decision**, read and never written: Faraday changes no byte of it,
  writes no copy, and makes no wallet file of Bitcoin Core's. A tile in
  Tools, Wallets, **Read a Bitcoin Core wallet**, takes a file in Files,
  and a file's row in Files offers the same tile where its first bytes
  are a SQLite database's.
- **SQLite is read by a reader of Faraday's own** of the part Bitcoin
  Core writes: the 100-byte header, the table B-tree of the one table
  `main` (key and value, both blobs) with its interior and leaf pages,
  overflow pages, varints and the record format, in the rollback-journal
  form Bitcoin Core writes. It is chosen over SQLite itself through
  `rusqlite` and its bundled C library: that brings some 250,000 lines of
  C under `unsafe` calls into the app, outside what `cargo vet` reviews,
  for a reader that needs one table. Faraday's reader has no `unsafe`
  and fails closed. A file in the WAL form, a page size or header field
  SQLite does not allow, a page reached twice, a cell past its page, a
  table other than `main` holding records, a lock or hot journal
  beside the file (its name compared without regard to ASCII case),
  a database version other than the 0 Bitcoin Core writes, a page that
  no table, index, overflow chain or the freelist reaches, or a `main` of
  more than 2^20 rows, a schema of more than 64 rows or a schema column (a name or the
  `CREATE` text) of more than 4,096 bytes, or a page named as the root of two tables or indexes
  is refused, and so is a record whose header names more columns than the
  table has. The bounds keep memory to three times the file (the file,
  its records copied once, and what the descriptors, labels and keys keep
  of them) and some 750 MB for the rows (under 700 bytes each, 2^20 at
  most), whatever tiny rows the file packs in, plus what parsing one
  descriptor's text costs, bounded by that record's size, which is at
  most the file's; failed records and unknown
  record types past 256 are counted, not kept, and a private key record
  with a value over 1,024 bytes or a label of an address over 128 bytes
  fails its record. A real wallet holds some thousands of records. It is a piece written here under §0 for
  this reason (one exists, and does not fit the rule that untrusted input
  is read without new `unsafe`), and is not cryptography, so
  `tools/lint-crypto.counts` does not count it.
- **The records are checked again.** The header's application id is the
  network's message start, and every key in the wallet is of that
  network; the database's version is the one Bitcoin Core writes; the
  wallet's flags include descriptors. Each `walletdescriptor` record's
  descriptor parses, its checksum is right, and its id is the hash of
  its text as Bitcoin Core computes it. In a wallet that is not
  encrypted, each `walletdescriptorkey` record's private key gives its
  public key and its stored hash of the two is right. The active
  receive and change descriptors (`activeexternalspk`,
  `activeinternalspk`) name descriptors the file holds. A record that
  fails is named with what failed, and the wallet is not called whole.
- **An encrypted wallet** shows without its passphrase what Bitcoin Core
  keeps in the clear: the descriptors (public, with their origins), the
  active ones, labels, flags, the `mkey` record's method and rounds, and
  which keys are encrypted. With the passphrase typed, the master key is
  opened (SHA-512 over the passphrase and salt for the record's rounds,
  then AES-256-CBC) and each `walletdescriptorckey` record's key with it,
  and each is checked against its public key as above. A wrong
  passphrase is said as such. One more piece written here goes into
  `written_here` in `tools/lint-crypto.counts`: Bitcoin Core's key from a
  passphrase and the opening of its encrypted keys; AES and CBC are
  RustCrypto's `aes` and `cbc`, SHA-512 `faraday-crypto`'s.
- **A descriptor is listed as Bitcoin Core lists it** (owner, 2026-11-10).
  A wallet Core made stores each descriptor as the master key with
  hardened steps and no origin (`pkh(tpub…/44h/1h/0h/0/*)`) and lists it
  as `pkh([fingerprint/44h/1h/0h]tpub…/0/*)`: the key at the last hardened
  step comes from the `walletdescriptorlhcache` records (the key is the
  descriptor's id and the key's place in it, the value the 74 bytes of an
  extended public key as a vector). The reader gives each descriptor in
  that form, checksum included, with the origin (the master key's
  fingerprint and the hardened path) and the cached key, so that Wallets,
  which refuses a key without an origin, can take it. Where the keys are
  checked (a plain wallet, or an encrypted one read with its passphrase),
  each cached key is checked in `faraday-keys` against the master private
  key: the hardened path is derived from it there, only a verdict leaves,
  and a cached key that does not match (a bad point included) fails its
  `walletdescriptorlhcache` record and the wallet is not whole; so is a
  cached key no master key's record was compared with (the descriptor
  has no key record for it), whatever the wallet's flags say. Where they
  are not, the cached key is taken as any descriptor with its origin is taken from a file: a bad point, depth,
  child number or (one step from the master key) parent fingerprint fails
  the descriptor's record. A descriptor that needs
  a cached key the file lacks, and a cache record that is not the shape
  Core writes, are failing records named so. A descriptor that is not
  ranged has no range. A record is refused (a failing record, `Range`) whose
  next index or range is negative or inverted, whose range is 1,000,000 indexes
  or more (Core's `CheckDescriptorRangeBounds`, "Range is too large": the
  size of the range, so a small range that starts high is read), whose next
  index is 1,000,000 or more (the owner's call),
  or whose descriptor has no `*` and stores a range of more than one index
  (Core calls such a file "Wallet corrupted": it derives the same script
  twice). A range of one index or none on a descriptor that is not ranged is
  ignored, as Core resets it. The cross-check compares every descriptor's listed
  text with Core's `listdescriptors` without private keys.
- **What the private keys do.** They are read into `faraday-keys` (F70,
  `docs/KEYS.md`), checked and wiped; they are not shown, not loaded as a
  key of the session and not written anywhere. The descriptors are
  public, and the result takes them to Wallets as Core's `listdescriptors`
  lists them (the listed form above, with the origins and the cached
  account keys), checksum taken off, as any descriptor with its origins is
  taken. Take to Wallets refuses a file that is not whole, with the
  reader's first line, and takes nothing from it.
- **`combo()` descriptors are listed, not taken** (owner's call,
  2026-11-10). A wallet made by Bitcoin Core's `migratewallet` holds a
  `combo()` descriptor (BIP 384) for each key of the legacy wallet and
  for its old HD chain, which the wallet reader does not take, and the
  file is whole all the same: a record whose text is exactly `combo(` of
  one key expression passes the checksum, the id, the range, the network
  and the origin checks as any descriptor does (the key read as a `pkh()`
  of the same key), and is listed under "Kept by Bitcoin Core, not
  taken", as stored, public keys only, and never sent to Wallets. Its
  private keys are checked against their public keys like the others';
  its cached account keys, if the file holds them, are not compared with
  anything, and nothing of it is listed but its text. Any other
  top-level function Faraday does not read still fails the record. Taking
  the others stays what the wallet is for; without this a migrated
  wallet could never be taken, and the refusal of a Berkeley DB file
  sends the person to `migratewallet`.
- **Refused:** a legacy Berkeley DB wallet, told by its magic number,
  with the line that Bitcoin Core's `migratewallet` makes a descriptor
  wallet of it; a SQLite file whose flags lack descriptors, or which
  holds legacy records (`key`, `ckey`, `hdchain`); a wallet of another
  network than Faraday's mode, said as a descriptor of that network is;
  a descriptor without its key origin, as everywhere. A record
  type the reader does not know is listed by name and count, not read.
  Transactions (`tx`) and the block locator are counted, not read.
- **A parser of untrusted input, fuzzed.** The SQLite reader and the
  record reader each have a fuzz target in `faraday/fuzz`, with seed
  files Bitcoin Core wrote.
- **Checked against Bitcoin Core and SQLite** (F160). The cross-check
  runs Bitcoin Core (`tools/crosscheck/core_node.py`) to make descriptor
  wallets plain, encrypted, watch-only and blank, with labels and
  imported descriptors on each test network, and compares what Faraday
  reads with Core's `listdescriptors`, with private keys where it has
  them, and `getwalletinfo`; files with a byte changed in a key, a hash,
  a checksum or the header are each refused by Faraday where Core's
  `loadwallet` refuses them or names the fault. The SQLite reader is
  checked against SQLite itself, through Python's `sqlite3`, over
  random databases of the one-table shape at every page size, with
  overflow pages and deleted rows.
- **Where it lives:** the SQLite reader in a crate of its own that holds
  no secrets, `faraday-sqlite`; the records and the screen in a
  `faraday-core` area; the opening of the keys in `faraday-keys`.
- **In Practice** the tile takes a sample regtest wallet in
  `faraday-samples`, plain and encrypted with the passphrase `faraday`,
  and the samples table of `docs/MODES.md` §6 lists it.
- **Faraday Starter does not read a `wallet.dat`.**

**Built so far:** the record reader (`faraday-core`'s `core_wallet`, with its fuzz target `core_wallet_records`), the key checks (`faraday-keys`'s `core_wallet`), and `core_wallet::read_file`, which takes a `wallet.dat`'s bytes, its name and the names beside it, reads it through `faraday-sqlite` and returns the wallet or a named refusal (a lock, journal or log beside it, a file that is not SQLite or not as Bitcoin Core writes it, a table other than `main` holding records, a database version other than 0, a page nothing reaches, more than 2^20 rows); the `core-wallet` cross-check area against Bitcoin Core (a wallet.dat read whole against `listdescriptors` and `getwalletinfo`, and changed files against `loadwallet`), over fixtures Bitcoin Core made (`tools/vectors/core-wallet/`). Not built: the tile, the samples and the fuzz target for the file read.
