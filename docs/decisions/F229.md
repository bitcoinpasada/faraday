# F229 A Bitcoin Core descriptor wallet's wallet.dat is read, never written, and its records checked again, through a SQLite reader of Faraday's own (2026-11-09)

**Kind:** Record
**Status:** Active, partly built
**Area:** wallets
**Held by:** review

**Why.** A person moving a Bitcoin Core wallet to cold storage, or
keeping one offline as a backup, has the file `wallet.dat` and no other
form of it. Faraday can say what the file holds and whether it is whole
without Bitcoin Core: its descriptors, which are active, its network,
and whether each private key is the one its public key says. Since
version 23 Bitcoin Core makes descriptor wallets, kept in a SQLite
database. The record layout is Bitcoin Core's own, published in its
source and used by that project alone; SQLite's file format is
published by SQLite; the descriptors are BIP 380 to 386. STANDARDS §0
takes one project's format only by a decision.

**Decision** (owner, 2026-11-05: read only, never edited or exported;
2026-11-09: Faraday's own SQLite reader, and a wallet's private keys
checked and wiped, never loaded).

- **A descriptor wallet's `wallet.dat` enters under STANDARDS §0 by this
  decision**, read and never written: Faraday changes no byte of it,
  writes no copy, and makes no wallet file of Bitcoin Core's. A tile in
  Tools, Wallets, **Read a Bitcoin Core wallet**, takes a file in Files,
  and a file's row in Files offers the same tile where its first bytes
  are a SQLite database's.
- **SQLite is read by a reader of Faraday's own** of the part Bitcoin
  Core writes: the 100-byte header, the table B-tree of the one table
  `main` (key and value, both blobs) with its interior and leaf pages,
  overflow pages, varints and the record format, in the rollback-journal
  form Bitcoin Core writes. It is chosen over SQLite itself through
  `rusqlite` and its bundled C library: that brings some 250,000 lines of
  C under `unsafe` calls into the app, outside what `cargo vet` reviews,
  for a reader that needs one table. Faraday's reader has no `unsafe`
  and fails closed. A file in the WAL form, a page size or header field
  SQLite does not allow, a page reached twice, a cell past its page, a
  table other than `main` holding records, or a lock or hot journal
  beside the file is refused. It is a piece written here under §0 for
  this reason (one exists, and does not fit the rule that untrusted input
  is read without new `unsafe`), and is not cryptography, so
  `tools/lint-crypto.counts` does not count it.
- **The records are checked again.** The header's application id is the
  network's message start, and every key in the wallet is of that
  network; the database's version is the one Bitcoin Core writes; the
  wallet's flags include descriptors. Each `walletdescriptor` record's
  descriptor parses, its checksum is right, and its id is the hash of
  its text as Bitcoin Core computes it. In a wallet that is not
  encrypted, each `walletdescriptorkey` record's private key gives its
  public key and its stored hash of the two is right. The active
  receive and change descriptors (`activeexternalspk`,
  `activeinternalspk`) name descriptors the file holds. A record that
  fails is named with what failed, and the wallet is not called whole.
- **An encrypted wallet** shows without its passphrase what Bitcoin Core
  keeps in the clear: the descriptors (public, with their origins), the
  active ones, labels, flags, the `mkey` record's method and rounds, and
  which keys are encrypted. With the passphrase typed, the master key is
  opened (SHA-512 over the passphrase and salt for the record's rounds,
  then AES-256-CBC) and each `walletdescriptorckey` record's key with it,
  and each is checked against its public key as above. A wrong
  passphrase is said as such. One more piece written here goes into
  `written_here` in `tools/lint-crypto.counts`: Bitcoin Core's key from a
  passphrase and the opening of its encrypted keys; AES and CBC are
  RustCrypto's `aes` and `cbc`, SHA-512 `faraday-crypto`'s.
- **What the private keys do.** They are read into `faraday-keys` (F70,
  `docs/KEYS.md`), checked and wiped; they are not shown, not loaded as a
  key of the session and not written anywhere. The descriptors are
  public, and the result can take them to Wallets as any descriptor with
  its origins is taken.
- **Refused:** a legacy Berkeley DB wallet, told by its magic number,
  with the line that Bitcoin Core's `migratewallet` makes a descriptor
  wallet of it; a SQLite file whose flags lack descriptors, or which
  holds legacy records (`key`, `ckey`, `hdchain`); a wallet of another
  network than Faraday's mode, said as a descriptor of that network is;
  a descriptor without its key origin, as everywhere. A record
  type the reader does not know is listed by name and count, not read.
  Transactions (`tx`) and the block locator are counted, not read.
- **A parser of untrusted input, fuzzed.** The SQLite reader and the
  record reader each have a fuzz target in `faraday/fuzz`, with seed
  files Bitcoin Core wrote.
- **Checked against Bitcoin Core and SQLite** (F160). The cross-check
  runs Bitcoin Core (`tools/crosscheck/core_node.py`) to make descriptor
  wallets plain, encrypted, watch-only and blank, with labels and
  imported descriptors on each test network, and compares what Faraday
  reads with Core's `listdescriptors`, with private keys where it has
  them, and `getwalletinfo`; files with a byte changed in a key, a hash,
  a checksum or the header are each refused by Faraday where Core's
  `loadwallet` refuses them or names the fault. The SQLite reader is
  checked against SQLite itself, through Python's `sqlite3`, over
  random databases of the one-table shape at every page size, with
  overflow pages and deleted rows.
- **Where it lives:** the SQLite reader in a crate of its own that holds
  no secrets, `faraday-sqlite`; the records and the screen in a
  `faraday-core` area; the opening of the keys in `faraday-keys`.
- **In Practice** the tile takes a sample regtest wallet in
  `faraday-samples`, plain and encrypted with the passphrase `faraday`,
  and the samples table of `docs/MODES.md` §6 lists it.
- **Faraday Starter does not read a `wallet.dat`.**

**Built so far:** the record reader (`faraday-core`'s `core_wallet`, with its fuzz target `core_wallet_records`) and the key checks (`faraday-keys`'s `core_wallet`), over fixtures Bitcoin Core made (`tools/vectors/core-wallet/`). Not built: the SQLite reader, the tile, the samples and the cross-check.
