# F194 A KDBX file is never refused for its contents: a damaged item is Unreadable, and every TOTP form is read for the codes page (2026-11-03)

**Kind:** Record
**Status:** Amended by F231
**Area:** security
**Held by:** keys.vault-contents-never-refuse

*Amended by F231 (2026-11-09): point 2's passphrase sentence is replaced: a passphrase belongs to exactly the key it names, and saving another asks nothing; the codex32 shares' grouping is narrowed to one threshold, identifier, index and key.*
*Amends F190 (2026-11-03): point 3's "fails closed for Faraday's items: ... refuses the file".*

**Why.** F190 point 3 refused a whole file for one damaged Faraday item.
A KDBX file is a standard format other programs open and edit, and a
person's passwords must not be locked out by one entry that a KeePass app
or a hand edit left in a form Faraday does not read. TOTP secrets are
written by several programs in several forms, and the codes page is more
use when it lists them all.

**Decision** (owner, 2026-11-03; `docs/VAULT.md` §7, §7.1;
`docs/TOTP.md` §4.1).

1. **What refuses a KDBX file** is only the format limits of
   `docs/VAULT.md` §7.1 (KDBX 3.1 and older, AES-KDF, Twofish or another
   cipher, Salsa20 as the inner stream, an empty passphrase), a wrong
   passphrase, a failed HMAC or a damaged file, and XML that is not well
   formed, has a DOCTYPE or an entity other than XML's five. The XML
   reader's format limits refuse it too: nesting past 64 elements, markup
   inside a text element the model reads, a protected value that is not
   canonical Base64 (damage), and a `Meta` or `Root` missing or repeated.
   A comment or a processing instruction anywhere is not refused. Nothing
   in the contents refuses it.
2. **A damaged Faraday item is Unreadable**: an unknown `faraday.kind`, a
   field its kind does not name, a required field missing, words that
   are not a BIP-39 phrase, a policy or descriptor that does not parse, a
   PEM block other than its field's, a `faraday.codex32`,
   `faraday.child` or `faraday.plan.{n}` that is not its TOML, a GPG key
   not of Faraday's shape, an entry with two
   fields of one name, two entries or groups with one UUID. The file opens;
   the item is listed with its title, UUID and the field or key; it is
   never loaded or used; the next seal writes it back unchanged. A
   `faraday.plan.{n}` or `faraday.signed.{tx}` that does not read is kept
   and named in the same way. Related secrets are not damage: several
   passphrases for one key, and several codex32 shares of one index and
   key, are each kept and read, and the app labels each ("1 of 2
   passphrases for key {fingerprint}") and warns when saving one that
   the vault already holds (Continue / Cancel; built later).
3. **A file that is not Faraday's**: with `faraday.format` missing it is a
   KeePass file Faraday did not make and opens with its entries; any other
   value than 1 opens it read-only with its Faraday items Unreadable; with
   `faraday.seals` missing or malformed the count starts again at 1.
4. **TOTP is read from every form in use**, for display only: `otp`,
   then KeePass 2's `TimeOtp-*` fields, then older KeePassXC's `TOTP
   Seed` with `TOTP Settings`. The codes page lists every entry with a
   secret, in any group of any open vault. Faraday writes only `otp` and
   never rewrites a TOTP field it did not make. HOTP and a form that
   does not read show a badge and never refuse the file.
