# F128 Upgrading a stick is the Starter's; Faraday writes no boot partition (2026-10-26)

**Kind:** Record
**Status:** Active
**Area:** stick

**Why.** Faraday had two ways to upgrade a stick: Settings → Upgrade a
Faraday stick on the device (F2), which copied the running Faraday's
boot partition over another stick's, and the Starter's Replace Faraday,
keep data (F11), which writes the release's boot partition from a
computer. The owner wants one way, the one that checks the image
against the signed release's manifest before it writes it, and a device
that keeps no code that opens or writes a boot partition.

**Decision** (owner, 2026-10-26).

- Faraday has no Settings → Upgrade a Faraday stick, on any medium. A
  stick is upgraded from a computer with the Starter's keep data
  (`docs/STARTER.md` §4.4), or written whole from a fresh image. A Pi
  card is written whole.
- The image carries no boot copier: no `faraday-boot` process, no
  account for it, no pipes, no upgrade marker. `faraday-grant` hands no
  boot partition to any process: a partition named `FARADAYBOOT` and the
  Pi's own card's first partition stay root's, whatever is beside the
  clean marker. It still hands every other partition to the disk
  process while the app is clean, authorises USB interfaces and gives
  later input and video nodes their owners.
- `faraday-boot` is a library alone: `find_release`, with which the
  Starter reads which Faraday a stick holds (`docs/STARTER.md` §4.1).
  The build ID's description and comparison (F5) are
  `faraday-core/src/build.rs`, which the Starter's keep data decides by.
- The Starter's keep data keeps F2 and F5's rules for what it writes:
  the same build is refused, an older Faraday over a newer stick and a
  dev build over a stick that does not hold one are warned about.

Amends F2, F5, F11, F67, F77 and F80, which describe Upgrade a Faraday
stick as built.
