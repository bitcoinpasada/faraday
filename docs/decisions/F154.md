# F154 Random bytes are taken from the source, an answer for every 32, or expanded by HKDF-Expand (2026-10-28)

**Kind:** Record
**Status:** Active
**Area:** security
**Held by:** standards.what-goes-in, crypto.tested

**Why.** The cryptography manifest (F148) showed places where Faraday
made several random values from one draw by a SHA-256 loop of its own:
the SLIP-39 split's randomness, the KDBX file's seed, IV, salt, inner
key and UUIDs, and the Seed XOR and codex32 random parts. No standard
describes such a loop and no published vector checks it, and the
cross-check feeds Faraday and the reference the same bytes, so it never
saw it: a construction of Faraday's own in the app, which STANDARDS §0
does not admit unreviewed.

**Decision** (owner, 2026-10-28).

1. **From the source.** A press that needs random bytes takes them from
   the session's randomness (`docs/OWN-RANDOMNESS.md`), one pooled system
   answer for every 32 bytes, each made into bytes by the documented
   fresh hash with the person's own randomness. With too few answers
   waiting, it takes none and says there is no randomness.
2. **HKDF-Expand where one draw serves a count not known in advance.**
   RFC 5869's HKDF-Expand with SHA-256 and a fixed label, checked against
   RFC 5869's test cases (a key's blinds, the BIP-340 aux of a test run).
3. **No loop of Faraday's own** makes random bytes. The MuSig2 `rand'`
   chain is the one left, until its committed fixtures can be made again
   with Bitcoin Core.

**Where:** `faraday/faraday-core/src/fresh.rs` (`take_bytes`),
`core/faraday-crypto/src/hash.rs` (`hkdf_sha256_expand`),
`faraday/faraday-core/src/keygen/mod.rs`, `faraday/faraday-core/src/vault/mod.rs`,
`core/faraday-backup/src/kdbx.rs`, `faraday/faraday-keys/src/operations.rs`,
`docs/OWN-RANDOMNESS.md` §1.
