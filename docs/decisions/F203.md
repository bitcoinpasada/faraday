# F203 A vault's name taken by a file nothing proves is a question: overwrite or save beside (2026-11-04)

**Kind:** Decision
**Status:** Active
**Area:** security
**Held by:** keys.vault-name-taken

*Changes `docs/BACKUP-FLOW.md` §14 item 3 and `docs/VAULT.md` §6, which said a file nothing proves is never written over.*

**Why.** A stick that missed a write holds a copy older than the one
opened. Its SHA-256 is one this session has not seen, so nothing proves it
is a copy, and the new file went beside it under a free name: the stale
copy stayed and the stick gained a vault for nothing. A vault's identity
is inside its encryption (F190 point 8), so without its passphrase
Faraday cannot tell an older copy of this vault from another vault of the
same name. Keeping hashes of earlier seals inside the vault was proposed
and refused by the owner. The person writing knows what the stick holds;
Faraday does not.

**Decision** (owner, 2026-11-04). When a vault is written and a file on
the stick has its name, ignoring case, and nothing proves that file is a
copy of this vault, nothing is written until the person answers:

1. **Overwrite**, by a hold, since it can destroy a different vault. The
   new bytes go under a hidden name and are read back; then the old file
   is removed and the new one takes its name, in the order `docs/VAULT.md`
   §6 gives. The answer names the SHA-256 of the file it was shown, and
   the disk process refuses it if the file has changed since.
2. **Save beside**, by a tap, under the free name the dialog shows
   (`name-2.ext`).

Going back from the dialog is neither: nothing is written, and the file
stays For the stick. The dialog says, as a fact, that Faraday cannot tell
which vault the file is and that overwriting destroys it even if it is
another vault. A file whose SHA-256 is that of a copy of another vault the
session knows is named so. A file that cannot be read for its SHA-256 has
no overwrite: only **Save beside**.

These stay as they are. A file the session has proved (`docs/VAULT.md` §6)
is replaced with no dialog, so an ordinary edit stays silent. A name no
file has is written with no dialog. No hash of an earlier seal is kept
inside a vault. A vault the backup flow is making new goes beside what the
stick holds under a free name with no dialog: the person chose
**A new vault beside them**, and no copy of it can be on a stick.

The disk process makes this check, since only it reads the stick's bytes.
What the app showed before, "the same vault, updated here" for a vault of
the same length and "another vault" for one of another length, guessed
from a file's length and claimed what nobody knew: both are gone.
