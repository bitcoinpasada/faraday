# F227 The nonce check remembers the signatures it checked in an open vault, and refuses a nonce one key used before on another message (2026-11-09)

**Kind:** Record
**Status:** Active, not built
**Area:** security
**Held by:** review

**Why.** The nonce check (`docs/FLOWS.md`, Nonce check) refuses a nonce
used twice inside one transaction, and forgets everything when the
session ends. A signer that signs two transactions with one key and one
nonce gives that key away to anyone who sees both signatures, and the
device can only see it if it remembers the first. A vault is the one
place the device keeps anything across a power-off, and it already keeps
each signed transaction's amounts (`faraday.signed.{tx}`, `docs/VAULT.md`
§7). Remembering signatures needs a record layout and a refusal of
Faraday's own: neither is a published standard (`docs/STANDARDS.md` §0).

**Decision** (2026-11-09).

1. **One entry per signature checked.** An entry is 96 bytes: the x
   coordinate of the signing key (32), the signature's nonce point (32:
   ECDSA's `r`, or BIP-340's `R.x`, on the key path, the script path and
   in final witnesses alike) and the message the signature verified
   against (32: its sighash). Only a signature that verifies is recorded:
   one not checked has no message, and is neither recorded nor compared.
   Signatures made here, a cosigner's brought into a spend and those of
   any file the Nonce check page opens are recorded alike.
2. **The record layout.** A vault keeps the entries of one transaction
   in one database custom-data value, `faraday.nonces.{tx}` (`{tx}` as
   `faraday.signed.{tx}` names it), each entry `{key}:{r}:{msg}` in
   lower-case hex, joined by `,`, with no version field; record type 17
   in `faraday-vault`'s records. A value that does not read is Unreadable
   (F194): kept as written, named, and not compared against.
3. **What reuse is.** The same key and the same `r` over a different
   message. The same three again is one signature checked twice (another
   file, a copy of the transaction) and no fault. Keys are compared one
   by one, never across keys: with ECDSA public key recovery anyone can
   make a valid signature over any public `r` under a key they derive, so
   a rule over every key would let a made file claim a key was given
   away.
4. **MuSig2.** A cosigner's partial signature that verifies
   (`musig::verified_partials`, F220) is recorded under the participant's
   key, with the x of its first public nonce point as `r` and SHA-256 of
   the sighash and the aggregate nonce as the message: the same round
   collected twice is the same entry, and that nonce in any other round
   is reuse. A public nonce with no partial is not recorded.
5. **The refusal.** A signature whose key and `r` a vault holds over
   another message is wrong: the nonce check names the key and the
   inputs, and nothing finishes, saves to a stick or shows as a QR code,
   on the spend or the Nonce check page. It fails closed and has no way
   past (STANDARDS §0, F136): once both signatures are public the key is
   given away, and not broadcasting the second is the last protection.
6. **Where it is kept.** The history is read when a vault is unlocked and
   written into every open vault when it is sealed, as signed amounts
   are; a record read from one vault is never copied into another. Up to
   10,000 entries a vault, the oldest transaction dropped first; at the
   vault's ceiling nonce records are dropped before signed amounts.
   Nothing is kept across a lock outside a vault.
7. **The setting.** Settings' **Nonce history** card, **Kept in an open
   vault** or **Off**; off, nothing is recorded, compared or shown, and a
   vault's records stay as written.
8. **The default is Kept in an open vault.**

**What it does not do.** It sees only signatures brought in or made here,
while the setting is on and a vault is open, per vault, up to its cap. A
clean history does not show a signer is honest: a dishonest signer can
leak a key without reusing a nonce. Sibling keys of one xpub that share a
nonce are caught only inside one transaction, by the rule already built.
An opened vault's entries name each checked input on chain by its `r`,
transactions of wallets not held here included, and a file vault's length
grows about 200 bytes a signature.
