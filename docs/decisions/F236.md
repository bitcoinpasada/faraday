# F236 The online apps' Send text tool shows any text as a QR code except a secret, by a rule of Faraday's own that fails closed (2026-11-10)

**Kind:** Record
**Status:** Active
**Area:** QR
**Held by:** standards.text-tool-refuses-secrets

*Amends F28: a text a person brings to the online apps gets a QR code, and a secret in it never does. Sits beside F33 and F181.*

**Why.** A person who copies a block header, a message to sign or an
invoice on an online computer had to save it into a file to send it to the
device. The online apps (the Starter and Faraday Demo) already show a file
as codes for the device's camera (Transfer's Send); the tool removes the
file step. Pasted text is usually copied from a live online session, so a
seed or a private key pasted into it would end as a code on an online
screen, which F28 rules out for a secret and F33 keeps out of the Starter's
flows.

**Decision** (owner, 2026-11-10).

- **The tool.** Transfer, in the Starter and in Faraday Demo, has a **Send
  text** card: a multi-line field, **Paste**, **Clear** and **Show as QR**.
  The code is the QR sheet's as for any public text: one code while it
  fits, else animated `ur:bytes`, with BBQr and Specter parts one choice
  away. The text is sent as given, its ends trimmed, and is wiped when
  Transfer is left.
- **A rule of Faraday's own that fails closed** (`docs/STANDARDS.md` §0,
  F136). The text is not shown as a code when the device's own classifier
  (`scan_read::secret_kind`, reused and never re-implemented, so a secret
  kind added there is refused by the tool too) names the whole text a
  secret, when the text read as a file is a secret wallet file, or when any
  part of it is one: a whitespace-separated token that is a WIF key, an
  extended private key in any form, an `nsec1` key, a silent payments spend
  key, a codex32 string, a `ur:crypto-seed` or a private `ur:crypto-hdkey`,
  an `otpauth://` URI, a run of 48 or 96 digits, a run of 12 or more
  words of one BIP-39 list (checksum or not) or of 20 or 33 words of the
  SLIP-39 list, or a PEM or PGP private key armour. The line under the
  field says what was found. A false refusal (twelve ordinary words in a
  row that are on a list) is the cost of failing closed.
- **The case it lets through.** Bare hex: a 64-hex string is a file's
  SHA-256, a transaction id or a block hash, and a raw private key has the
  same form. Refusing it would refuse the file-hash use, so it is shown.
  This is the one legitimate case (F136) and the only one; there is no
  setting and no hold that shows a refused text.
- **The cap.** Text is limited to 16 KiB: at the medium part size and the
  default speed that is about a hundred frames. Larger text is sent as a
  file, which Send takes up to the file envelope's limit.
- **Why the text tool refuses and file Send does not.** A file the person
  chose in Downloads is the test area's import path (F181): Transfer's Send
  of a secret file stays as it is, shown on the sheet marked Secret. Text
  is pasted from a session, and refused.
- **Held by** the rule `standards.text-tool-refuses-secrets` in
  `tools/impact.toml` (a change to what the classifier names, or to the
  tool, is reviewed against this decision) and by the tool's tests.
