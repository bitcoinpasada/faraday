# F254 An output is change only of the wallet the inputs spend, and a wallet of several keys comes in only through one sheet that shows its keys (2026-11-14)

**Kind:** Record
**Status:** Active
**Area:** wallets
**Held by:** review

*Amends F135. Point 1 is built (`core/faraday-psbt`); points 2 and 3 are not yet built: `docs/FLOWS.md`'s Open line names them.*

**Why.** F135 verifies change against every registered wallet that holds
a loaded key, and lets a wallet of several keys in with no sight of its
other keys: from a file, a code, a stick's boot import or visit it is
added with no confirmation, and the register sheet of a spend shows only
fingerprints and paths, which whoever wrote the PSBT chooses. A
coordinator that knows one extended key of the person's (every
watch-only coordinator holds their single-key account key) can write a
1-of-2 over it and a key of its own, plant it beside a payment, and send
the rest of that payment to it: the output read "Change · Verified" and
the amount sent left it out. `holds` proves only that one key is the
person's; nothing showed the others or tied change to the coins being
spent. Coldcard and Ledger show every cosigner's extended key when a
wallet is enrolled, and Bitcoin Core calls an output change only of the
wallet that spends.

**Decision** (owner, 2026-11-14; `core/faraday-psbt/README.md`,
`docs/WALLETS.md` §3.3, `docs/FLOWS.md` Spend tab):

1. **Change is of the wallet spent.** The person's wallets are each
   loaded key's single-key accounts (BIP 44, 49, 84, 86, one per account
   path) and the registered wallets that hold a loaded key (F135 point
   4). An output verified as an address of one of them is change only
   where every input verified as the person's spends that same wallet.
   Otherwise it is a **transfer** (`OutputKind::Transfer`): counted in
   the amount sent, drawn under Sends with the name of the wallet it
   pays into, with a Caution ("output 1 pays another of your wallets,
   not the one these coins are spent from; it counts as sent"). A
   transfer is never blocked: a consolidation into another wallet of the
   person's is a payment they may mean. A transaction none of whose
   inputs is the person's signs nothing here, and its outputs are read
   as before. A wallet claim whose script is not the output's still
   tries the single-key rule before it is called a spoof, so a wallet of
   several keys over a single-key account never takes away that
   account's own change. The fee-bump judge and Compare follow it: a
   transfer is not the person's change on either side.
2. **One confirmation for every wallet of more than one key**, however
   it comes in: a PSBT's register offer, a file, a code, the boot import,
   a stick visit, Restore and Create alike; only a vault's own wallets
   loaded at its unlock are exempt. `Session::add_policy` holds such a
   wallet back, as F132's key path wallet is held, until the sheet's
   hold. The sheet (DESIGN §4.13's dialog) shows the shape and name, and
   per cosigner the fingerprint, the path, "Yours" where a loaded key
   gives it, and the whole extended public key (mono, in groups of four,
   wrapped, never cut); then the descriptor checksum, a tr() tree's key
   path line (F132), and one line saying to compare the checksum and
   each key with every other signer's device or the wallet's backup.
   F135 point 3's sheet is this sheet, its checks kept. A cosigner that
   is the person's own key at a single-key account path (BIP 44, 49, 84,
   86) is not refused, since some coordinators build wallets so, but its
   row says so in place of "Yours" ("Yours · your single-key account").
3. **The change row names its wallet**, and reads "Change" only for an
   address on chain 1; the person's own wallet's address on chain 0 is
   drawn as their receive address ("Receive" with the wallet's name).

**Not changed.** F135's rule for signing a script of several keys and
its refusals; two wallets on one BIP-48 account told apart by script; a
spend from a wallet into itself still a self-transfer; a watch-only
single-key wallet file still loads with no hold.
