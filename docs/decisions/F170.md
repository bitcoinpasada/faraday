# F170 The vault area's code stays together for auditability, not split per screen (2026-10-29)

**Kind:** Record
**Status:** Active
**Area:** repository
**Held by:** structure.vault-together

**Why.** The vault's screens (Vaults, Unlock, CreateVault, a vault's
contents) share one module's state and logic. `lint-layout` marks files
over 2,500 lines and the screens check (F164) lists the actions a
screen does not offer, and both are easier to satisfy by splitting the
module per screen. A split spreads one reviewable unit across files a
reader has to hold together, which costs more in auditability than the
marks gain.

**Decision** (owner, 2026-10-29).

1. **Stays together.** The code in `faraday/faraday-core/src/vault/`
   is not split per screen to satisfy a lint. `vault/screen.rs` and
   `vault/mod.rs` stay over `lint-layout`'s 2,500-line mark on
   purpose; `tools/lint-layout.counts` keeps them as they are. As
   every count, they may only fall: a change that shrinks them for its
   own reasons is fine, a split into per-screen files is not.
2. **The screens exceptions are accepted.** The "not on this screen"
   entries in `docs/crypto/actions.toml` (`[[action.screens_not]]`,
   counted in `tools/lint-crypto.counts`, F164) that come from one
   module serving several vault screens are the cost of that. Each
   keeps a true written reason. Reducing them is nice to have, not
   necessary.
3. **The one route if they are reduced.** A smarter screens check that
   follows each screen's presses and drawing through `check.py`'s call
   graph (`docs/CRYPTO-LEARN.md` §9.2), which moves no product code.
   Not a split.

The vault's cryptography lives in `faraday-vault` and `faraday-keys`;
this decision does not concern it.
