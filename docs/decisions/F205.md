# F205 One kernel patch of Faraday's own on the Pi: a failed read of a later EDID block keeps the blocks before it (2026-11-04)

**Kind:** Record
**Status:** Active
**Area:** security
**Held by:** review

*Makes one exception to F153's "No kernel patch of Faraday's own": the rest of that rule stands.*

**Why.** A read of EDID block 2 or later takes three I2C messages.
`i2c-bcm2835` starts each next message from its TXW interrupt, which holds
for one write followed by a read; with three, its bus log shows the read
ending short, every time it failed. The 6.1 kernel then drops the whole EDID,
so a monitor with three or more blocks gave no modes and no framebuffer on
most boots, on two cables and both of its ports. A newer kernel does not cure
it: the driver's line is the same in Raspberry Pi's 6.18, and stock Raspberry
Pi OS on 6.18.50 read 0 EDID bytes on the same monitor, keeping 1920x1080 only
from an earlier read in that boot. The mainline change that lets a failed read
give the fallback modes, carried beside this patch, gives 1024x768 at best.

**Decision** (owner, 2026-11-04; `docs/IMAGES.md` §3.2).

1. **The Pi carries this one patch of Faraday's own**
   (`faraday/image/boards/pi3/linux-patches/0002-…`). When a read of an
   extension block fails, the blocks read before it are kept and the rest are
   marked invalid. Nothing else about the EDID's checks changes. With only
   this and the mainline patch, the test image gave a picture on 3 of 3 boots
   on that monitor.
2. **It goes when it is no longer needed:** when a kernel the Pi moves to, or
   `i2c-bcm2835` itself, reads such an EDID reliably. Any kernel update has to
   carry it or show it is not needed.
3. **Any other kernel patch of Faraday's own needs its own decision** (F153).
