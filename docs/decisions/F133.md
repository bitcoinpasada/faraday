# F133 The Starter writes a boot file the person signed, once it is checked to be the release's own (2026-10-27)

**Kind:** Record
**Status:** Active
**Area:** Starter
**Held by:** tests

**Why.** With Upgrade a Faraday stick gone (F128), a stick upgraded with
the Starter's keep data gets the release's unsigned
`EFI/BOOT/BOOTX64.EFI`. A person who signs Faraday's boot file with their
own Secure Boot db key (Faraday's Secure Boot tools, the key in a vault)
lost that signature at every upgrade, and the old way round it, signing
on a spare stick and upgrading from it on the device, went with Upgrade.

**Decision** (owner, 2026-10-26, option 1).

- Make a Faraday stick's What to write offers, for a stick for a PC or
  an Intel Mac, under **Boot file**: "The release's (unsigned)", ticked
  at first, or "One I signed". The second lists the `.efi` files in the
  Downloads folder the Starter's Transfer uses, the newest first; a file
  dropped on the window is taken as one tapped. There is no system file
  dialog. Continue waits until a signed file is taken. A Pi card and a
  stick for a Mac with M1 or M2 have no choice.
- Only its signature is taken. Its Authenticode image hash
  (`faraday_sb::pe::image_hash`, which leaves the signature out) must be
  the image hash of the release's `BOOTX64.EFI` as the payload checked
  against its manifest holds it, and its certificate table one signature
  alone at its end. The file written is built from the release's own
  bytes with that file's checksum, certificate-table entry and table
  (`faraday_sb::pe::transplant`), and the signature must hold over it by
  a certificate it carries (`faraday_sb::pe::signer`). Otherwise it is
  refused by name: "This is not this release's boot file", "This boot
  file holds more than the release's program and one signature", "This
  boot file is not signed" or "This boot file has no signature that
  holds". Which key signed it is not judged: the computer's db does
  that. What to write and Confirm show the certificate's name, the
  file's own choice, stripped of control and direction characters, and
  its SHA-256, which the person compares with their db key's.
- The order carries the file's full path and the SHA-256 it had when it
  was taken. The writer, the elevated copy on Windows
  (`--boot-file PATH --boot-file-sha256 HEX`), reads it again, refuses
  it when its SHA-256 differs, and checks it against the release again,
  before the disk is touched. The elevated copy takes only a path on a
  drive (`X:\…`: no UNC, `\\?\` or `\\.\` path, stream, `.`, `..` or
  device name), opens the file itself and never a reparse point's
  target, and sends back which file could not be read but no system's
  words. Sending the file's bytes over the writer's pipe instead was
  not taken: the pipe carries only the elevated copy's reports, and its
  non-blocking mode would need a second protocol that cannot be tried
  without Windows.
- What is written is the release's image with that one file written
  over where it is in the boot partition (`faraday_fat::Volume::rewrite_in`):
  its clusters, the clusters it grows by, its folder entry and the FATs
  differ from the release's, nothing else. Read back and compared as
  any write is. The manifest stays the release's; the signed file is
  not in it.
- The device still writes no boot partition (F128): the signing stays
  on Faraday, the writing on the Starter.

Amends F11 and F128, which describe keep data writing the release's
boot partition as it is.
