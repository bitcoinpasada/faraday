# F162 Anti-exfil in both directions, Faraday as the host first, FractalEncrypt's exchange in dev builds only behind `experimental` (2026-10-29)

**Kind:** Record
**Status:** Active
**Area:** crypto
**Held by:** standards.experimental-dev-only

**Why.** A signing device can hide its key in the nonces of the
signatures it makes, and two signatures can carry out a whole seed
(`docs/learn/13-nonces.md`). Anti-exfil lets a second party, the host,
add randomness to each nonce that the signer cannot choose, and check
every signature against it. The only deployed form is Jade's, over USB
or Bluetooth with Blockstream's own host. FractalEncrypt's air-gapped
protocol carries the same cryptography (libsecp256k1-zkp's `ecdsa_s2c`)
in four stages over QR codes, but it is an alpha, written mostly by AI
models and reviewed by AI models with no human audit, under an
unregistered UR type; no BIP defines anti-exfil or PSBT fields for it.
A review for the owner (2026-10-29) found the cryptography right,
reproduced FractalEncrypt's vectors byte for byte with btclib, and found
that the protection a person gets rests mostly on the host's rules,
which the alpha's host loosens. It also found two errors in Faraday's
spec: the host checks with `rho`, which is not public information, and
a stateless signer cannot refuse a second host commitment for an input.

**Decision** (owner, 2026-10-29). `docs/ANTI-EXFIL.md` is the spec.

1. **Both directions.** Faraday checks other signers, so a person is
   protected from someone else's device, and Faraday signs with
   anti-exfil, so a person is protected from Faraday. Nothing assumes
   Faraday is honest.
2. **Faraday as the host first.** Offline, Faraday draws `rho`, sends
   the host commitment, takes the signer commitment, reveals `rho`,
   makes both checks, and wipes `rho`, which it never saves and which
   never touches an online machine. It sits between the coordinator and
   the signer in the QR flow: Tools, Check a signer, and later Spend
   when a cosigner signs.
3. **`rho`'s source.** Drawn as every other secret Faraday makes is:
   the system's randomness, with every source the person adds (the
   Randomness row at the press, F157). No mode of its own and no minimum
   of the person's sources. `rho` is never written down or kept.
4. **The encoding, in dev builds only.** FractalEncrypt's four-stage
   protocol, multi-slot layout, the older layout refused. By
   `docs/STANDARDS.md` §0 an unpublished standard stays out of every
   shipped app: the app's part is behind one cargo feature,
   `experimental`, off by default and on only in a dev build (a dev
   image, F136, or a developer's own `cargo` run); a dev image is never
   shipped, as `release=1` refuses one. No release and no test release
   carries the feature. Accepting fields beyond BIP-174 is in dev builds
   only. Faraday supports whatever QR scheme Jade publishes, and
   FractalEncrypt's once it is published. The review recommends the
   four-stage semantics in BIP-registered PSBT input fields with a
   version and a session id, and Faraday intends to help write that
   draft BIP. STANDARDS §0.1 lists it. No USB path to a Jade: QR only.
5. **The host's rules**, each a refusal with no way past it (F136):
   protected signing is required, with no fallback to ordinary signing
   when the exchange fails; no fresh `rho` for the same payment after an
   abort, the retry made with the same `rho` and the same `R1` required,
   and aborts counted and shown; both checks; every declared length
   capped before it is allocated; and only the allowed fields taken from
   the signer's reply.
6. **Faraday as the signer, second.** The nonce is derived from the host
   commitment exactly as `ecdsa_s2c` does, from `rho` at the last stage,
   and never ground for low R, so anti-exfil signatures are 71 to 72
   bytes. Stateless between stages. Its hosts: FractalEncrypt's Sparrow
   fork today, upstream Sparrow the goal if it adopts the exchange, and
   a second Faraday device with the person's dice; the spec says what
   each protects against. Taproot is not covered by any form
   (libsecp256k1 pull request 1140 is unmerged).
7. **The Nonce check.** An anti-exfil signature is deliberately not an
   RFC 6979 nonce: when one arrives with its exchange, the Nonce check
   makes the exchange's checks instead and says so; without it, the
   Nonce check stays as it is. Until anti-exfil exists, in dev builds,
   the shipped app does not change.
8. **References.** libsecp256k1-zkp, at or after commit `a69a662`, and
   libwally for the cryptography; btclib, already vendored, which
   reproduces FractalEncrypt's vectors byte for byte. FractalEncrypt's
   vectors are encoding fixtures only, labelled alpha, AI-written and
   AI-reviewed, no human audit.
9. **How it is described.** Experimental. Anti-exfil matters and needs
   to move toward a standard quickly. What each form protects and does
   not: not a signer that lies about addresses, not a malicious host
   that builds a bad transaction, not bad entropy.
10. **Corrections to the spec.** The host needs `rho`, and `rho` stays
    secret for the life of the key: a leaked `rho` and a backdoored
    signer give the key. A stateless signer does not refuse a second
    host commitment; its last-stage nonce is derived from `rho` and
    never ground.
11. **Coming into the app** is the owner's decision, in a decision that
    amends this one, once a published standard carries the exchange.

**Where:** `docs/ANTI-EXFIL.md`; `docs/STANDARDS.md` §0.1;
`docs/crypto/actions.toml` (`anti-exfil`); `docs/learn/13-nonces.md`;
`tools/impact.toml` (`standards.experimental-dev-only`), held, once the
feature exists, by `tools/lint-keys-tests.sh` and
`faraday/image/build.sh`.
