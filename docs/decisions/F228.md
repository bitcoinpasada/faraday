# F228 Core Lightning's hsm_secret enters Faraday as a source of Lightning node key, plain or encrypted, checked against Core Lightning's code and not on the device (2026-11-09)

**Kind:** Record
**Status:** Active, the key side built and the screen not
**Area:** keys
**Held by:** review

**Why.** Lightning node key gives a node's key from ldk-node's BIP-39
words and from LND's aezeed (`faraday/faraday-keys/src/lightning.rs`).
A Core Lightning node keeps its root secret in one file, `hsm_secret`,
and has no words of its own unless it was made from BIP-39 words by
`lightning-hsmtool generatehsm`. A person who keeps that file offline
can then see on Faraday which node it is. The format is Core Lightning's
own: published in its source and documentation, used by that project
alone, a BIP, SLIP or RFC none of it. Its cryptography is standard:
HKDF-SHA256 (RFC 5869), and for the encrypted form Argon2id (RFC 9106)
and libsodium's `secretstream` over XChaCha20-Poly1305. `docs/STANDARDS.md`
§0 takes one project's published format only by a decision, as F219
did for KEF.

**Decision** (owner, 2026-11-05).

- **`hsm_secret` enters under STANDARDS §0 by this decision**, as one
  project's published format, used by that project alone, and checked
  against Core Lightning's code and not on a device. It is a third source
  on Lightning node key, beside an LND cipher seed and BIP-39 words, read
  from a file in Files, and Core Lightning's node is also given from
  BIP-39 words.
- **Three forms are read, told apart by length** as Core Lightning's
  `detect_hsm_secret_type` does. The plain form is the 32
  bytes of the secret and nothing else. The encrypted form, which
  `lightning-hsmtool encrypt` and `--encrypted-hsm` write, is 73 bytes:
  a 24-byte `secretstream` header, then the secret sealed as one message
  (a tag byte, 32 bytes and a 16-byte tag), under a key Argon2id makes
  from the passphrase with Core Lightning's fixed 16-byte salt and
  libsodium's moderate limits (three passes, 256 MiB). The passphrase is
  typed on the device; a wrong one or a changed byte fails the tag and
  is said as one refusal, the passphrase or the file wrong. A file shorter than 32 bytes is
  refused, an empty one included. Every other length is the mnemonic
  form (below). The file is never
  decrypted anywhere but on the device: Faraday does not ask a person to
  run `lightning-hsmtool decrypt`, which writes the plain secret on the
  online node.
- **The mnemonic form is read too** (owner, 2026-11-10). Core Lightning
  v26.06 writes it for every new node, with or without `generatehsm`
  (`create_hsm` in `hsmd/hsmd.c`): a 32-byte hash, all zero when the
  words have no passphrase and else the SHA-256 of the 64-byte BIP-39
  seed, then the BIP-39 words as text. Faraday reads it as
  `extract_mnemonic_secret` of `common/hsm_secret.c` does: the words
  taken from the file, English only, the node secret the first 32 bytes
  of the seed. A passphrase is asked when the hash is not zero and is
  checked against it; a wrong one is one refusal, and a passphrase given
  for a zero hash is refused, as Core Lightning refuses it. Faraday
  refuses what Core Lightning might read differently: text that is not
  UTF-8, a NUL (Core Lightning stops there), words in other than
  single-space form (a newline or extra space), words that are not valid
  English BIP-39 words, and a file longer than the longest 24 words
  need. Faraday's BIP-39 takes 12 to 24 words, so the 27 and 30 words
  libwally, and so Core Lightning, also takes are refused. A passphrase
  Faraday's BIP-39 cannot take (not printable ASCII, or past 256 bytes)
  on a mnemonic-form file is refused with a line of its own, as the same
  passphrase is for words, not as a wrong one (Faraday's rule, the
  passphrase rule of its BIP-39; Core Lightning takes any bytes). Words in the file are secret, kept in wiped buffers in
  `faraday-keys`.
- **The node key is Core Lightning's.** Its private key is HKDF-SHA256
  with the secret as input key, the info `nodeid` and a 4-byte salt
  counting up from 0, taken again with the next salt while the 32 bytes
  are not a valid secp256k1 key, as Core Lightning's `hsmd` derives it.
  The network changes nothing: one secret is one node id on every
  network. The node id, its private key and what Faraday does with them
  are those of the other two sources: the public key shown, the private
  key leaving only through `lightning::Node`'s named reveals.
- **Core Lightning's node from BIP-39 words too** (owner, 2026-11-09).
  `lightning-hsmtool generatehsm` makes the `hsm_secret` from BIP-39
  words and their passphrase: the first 32 of the 64 bytes BIP-39's
  seed gives. Lightning node key gives that node's id from loaded BIP-39
  words as well, beside ldk-node's from the same words, each named by the
  program it is for, the secret made as `generatehsm` makes it and the
  node key from it as above. The cross-check gives Core Lightning's code
  the same words and passphrase and compares the node id.
- **Thirty-two bytes cannot say they are an `hsm_secret`.** Any 32-byte
  file reads as one, so the result shows the node id for the person to
  compare with the one their node reports (`lightning-cli getinfo`);
  Faraday claims no more than that the file gives this id.
- **Left out:** the node's on-chain wallet (Core Lightning's BIP-32 seed
  from the same secret under another HKDF info), channel keys, and a
  `hsm_secret` as a key of the session; the secret gives a node key and
  nothing else. An older form Core Lightning no longer writes is not
  known to exist, and a file that is none of the three is refused.
- **Key material stays in `faraday-keys`** (F70, `docs/KEYS.md`): the
  file's bytes are read into a wiped buffer there, the passphrase as
  `SecretText`, and the read runs as a job off the main thread
  (`docs/WORKERS.md` §6), as an aezeed's does; HKDF is `faraday-crypto`'s
  (F180), Argon2id is the `argon2` crate the vault already uses.
- **One more piece written here:** `written_here` in
  `tools/lint-crypto.counts` goes up by one for opening libsodium's
  `secretstream`, one message under XChaCha20-Poly1305, since no crate a
  publisher F71 trusts offers it; its ChaCha20 and Poly1305 are
  RustCrypto's.
- **Checked against Core Lightning's code and not on the device.** The
  `lightning` cross-check area takes Core Lightning's own code, pinned
  and vendored under `tools/reference/`, as it takes LND's: random
  secrets plain and encrypted, under random passphrases, random
  mnemonic-form files with and without a passphrase, the node id
  each gives, and changed bytes, wrong passphrases and wrong lengths,
  each of which both refuse; the opening is also checked against
  libsodium itself. No Core Lightning node is run on a Faraday device.
- **In Practice** the source takes only a published sample, a plain and
  an encrypted `hsm_secret` with the passphrase `faraday`, in
  `faraday-samples` and the samples table of `docs/MODES.md` §6, as the
  LND cipher seed row takes only LND's published seed.
- **Faraday Starter does not read an `hsm_secret`.**
