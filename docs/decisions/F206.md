# F206 A file vault grows by itself: no size to choose, 32 KiB steps, up to 256 MiB as long as it fits in memory (2026-11-04)

**Kind:** Record
**Status:** Active
**Area:** security
**Held by:** keys.vault-memory-need

*Not built: the app still chooses one of four sizes. `docs/VAULT.md`'s Open line says what is left.*

**Why.** F190 point 4 kept four file sizes, chosen when a vault is made.
A person who has a KDBX file with attachments should be able to use it,
whatever it holds, and a person making a vault should not have to guess
how much it will hold. A size chosen too small also stops a lock. A
ceiling this high changes what the code can assume: a file can be larger
than the memory left, Rust aborts on an allocation that fails, which
would end another open vault's unsealed changes, and a size read that
writes the whole document for each change (28 ms at 3.6 MB used, 68 ms
with eleven changes, on the build machine) would take seconds.

**Decision** (owner, 2026-11-03). It amends F190 point 4; QR vaults are
not affected. `docs/VAULT.md` §2, §5, §8 and §9 are how it reads.

1. **No size is chosen.** A new vault is 32 KiB of plaintext. Every seal
   pads to the smallest multiple of 32 KiB that holds the contents, so a
   vault also shrinks when what it holds does. Nothing is remembered of
   the size before.
2. **The ceiling is 256 MiB of plaintext**, 268,435,456 bytes, for the
   reader and for a seal; the file is then 268,445,021 bytes (owner,
   2026-11-04: lower than the 1 GiB first planned, for what point 4
   measured). A file whose stored body is over 256 MiB and an eighth is
   refused from its length, as now.
3. **Attachments are only carried** (owner, 2026-11-03). No viewer is
   planned.
4. **Memory comes before size.** A check of what the system has free, the
   figure §3.1 of `docs/VAULT.md` names, comes before a file is read,
   before an unlock starts and before a seal starts, against one function
   in `faraday-core`: 2 × the file to read it; Argon2id's memory, 2 × the
   file and 100 MiB to unlock it; and, once it is decrypted and to seal it,
   Argon2id's memory, 16 × the document, 2 × the attachments and 100 MiB.
   Measured on 256 MiB of real entries, the peak is 15 × the document; on
   one 256 MiB attachment, 2 ×. What does not fit gets a plain message and
   takes no memory. The factors only fall, by a measurement. Checking first is the defence, since on Linux
   an allocation that succeeds proves nothing; file-sized buffers are also
   allocated so that a failure is an error, which covers Windows and a
   32-bit address space (the check takes at most 2 GiB free there).
   A machine that says nothing of what it has free opens a file of at most
   4 MiB, as it opens only the 64 MiB step (`docs/VAULT.md` §3.1).
5. **A compressed file is checked again** once it is decrypted: gzip's
   stated length, in bytes the HMACs verified, is checked against the
   ceiling and against point 4's function before the one buffer of that
   length is allocated, and inflating cannot write past it.
6. **A file is not held more often than it must be.** A vault's slot keeps
   the digest of the file it opened, not the file; attachments share the
   decrypted body's buffer; Argon2id runs and is freed before a seal builds
   anything; a seal encrypts and frames straight into the file it writes.
7. **A vault's file travels in pieces**, off the screen's thread: the frame
   between the app and the disk process keeps its limit of about 18 MiB,
   so a frame's stated length still cannot ask for more. `MAX_READ` stays
   18 MiB for every other file; a file that begins as KDBX 4 takes the
   vault's limit.
8. **An edit does not cost the file's size.** The bytes a seal takes are
   the document's as opened, measured once when it opens, plus an upper
   bound for each change, from the change alone. Under the ceiling that
   sum is the whole check: no copy, no write. Only past it is the document
   written to count exactly. An edit the seal would refuse is found from
   the one entry it touches, against what the open already read. The seal
   still makes every check itself: a wrong bound stops a lock, it does not
   lose or damage a vault.
9. **The picker's room checks go.** What remains is the ceiling: an edit
   past it is refused, a lock past it stops and says by how many bytes,
   and a transaction's signed amounts lose their oldest only there.
10. **What a length says is said plainly** (`docs/VAULT.md` §9): how much a
    vault holds, to within 32 KiB, and between two copies, that it grew or
    shrank. This replaces F189 point 4's and F190 point 4's promise that
    the length says only which of a few sizes it is. The padding that
    remains hides single small changes and how little a small vault holds.

**What this binds.** A change to what opening or sealing a file vault
holds in memory keeps point 4's function true.
