# F293 A plan whose SLIP-39 set is not its key's keeps that set's placed shares as kept old shares (2026-11-19)

**Kind:** Record
**Status:** Active
**Area:** backup
**Held by:** review

*Amends F285 and F276 (2026-11-17, 2026-11-16): a plan's SLIP-39 set that is not its key's gives way to the key's, its placed shares kept on the plan as old shares until destroyed, as F285 keeps Seed XOR's old parts; Convert's Rotate the set records the new set on the key whose set it rotates (F285 point 7 and F276's "one set of a kind per key" no longer hold for that case); the rest of both holds.*

**Why.** A plan can hold a SLIP-39 set that is not its key's: a plan
made by another wallet using the same key, a key whose set was rotated
in Convert, or a second split. Every SLIP-39 set of a seed splits the
same master secret, so the old set's shares still rebuild the key until
they are destroyed. Dropping them from the plan (tried and reverted)
made "any one place lost" and what a place's finder holds stop counting
shares that still open the wallet, without a word to the person.

**Decision** (owner, 2026-11-19).

1. **What a set is.** Two SLIP-39 sets are the same set when their
   identifier, iteration exponent, group threshold, group count and each
   group's member threshold agree: what every share carries and what
   SLIP-39 checks before it combines shares. Which members were made and
   a group's member count are not compared (a share carries neither),
   and neither is the extendable flag (the key's facts do not keep it).
   The plan's set and the key's being the same set, a share the plan
   placed that the key's set does not list as made stays where it is, a
   share of the set, and the plan's set lists it as made beside the
   key's members: it combines with the key's shares, so dropping it would
   understate what a place gives. A set rotated with its extendable flag
   clear keeps its identifier and may be the same set by these facts
   though its shares do not combine with the old ones; Faraday's own
   splits are extendable, so this is only a set typed in from elsewhere,
   and the plan counts the two as one.
2. **A plan whose set is not its key's.** Opened on Back up, a plan whose
   SLIP-39 set is not the same set as its key's keeps its placed shares
   at their places as kept old shares, counted, the old set recorded
   whole, and the key's set becomes the plan's current one, not placed
   yet: the safe reading, since the person has not said they are
   destroyed. A share of the old set the plan never placed is not on the
   map and is not asked about. Where the key's set is the same set as one
   of the plan's old sets, the plan stays as it is (a vault's stale copy
   of the key cannot bring a set back; codex32 does the same for a set
   rotated away).
3. **What identifies a kept share.** Its seed, its old set's identifier,
   its group and its member index: `What::Slip39Kept(seed, identifier,
   group, member)`, written on a spot line as
   `slipk{seed}.{identifier}.{group}.{member}`, the identifier in
   decimal as the `slip39` line writes it. The old set is kept whole on
   the plan as one line, `slip39old`, with the `slip39` line's value
   (seed, identifier, exponent, group threshold, groups with their
   members made). A seed's old SLIP-39 sets have distinct identifiers;
   a plan holds at most four old SLIP-39 sets of a seed (as F285's four
   old Seed XOR sets, counted per kind). A kept share of no old set, of
   a member its old set did not make, or anywhere but a place's paper is
   refused, and so is a plan breaking either limit. An old set's line is
   dropped once none of its shares is on the map. Nothing secret is
   recorded: no share, no word.
4. **When the plan cannot keep the old set.** Where keeping it would
   break a limit of point 3 (four old sets of the seed already, or its
   identifier already an old set's), the plan keeps its own set, as F285
   does for Seed XOR when `xorold` cannot take the old parts, and Back
   up's section says "This plan keeps another set than the key's.
   Destroy old shares to take the key's set." until older kept shares are
   destroyed; the next opening then takes the key's set. Back up's Seed
   XOR section says the same line in the same case, with "old parts" for
   "old shares" (owner, 2026-11-19).
5. **What a kept share counts for.** SLIP-39 is threshold-based: an old
   set rebuilds the key while its group threshold of groups each still
   has its member threshold of kept shares on the plan, wherever they
   are; then "any one place lost" and what a place's finder holds count
   it as the set it is, and a kept share counts toward its own old set
   only. Old and new shares never combine, and shares of two old sets
   never combine. A kept share has no checklist item and no Check my
   copy; the shares item counts the current set only. While an old set
   still rebuilds the key, the section says "The old shares still kept
   rebuild this key."
6. **Where the person sees them.** Back up's other paper forms section
   gains a SLIP-39 part, shown while the plan has a SLIP-39 set or kept
   old shares: it lists each kept share by its group, its share and its
   place, "Old share: group 1 share 2 · Place 2", with **I destroyed it**
   (it leaves the plan) and **Still kept** (it stays, marked), then "Old
   shares still kept: Place 1, Place 3" and the line of point 5. A kept
   share's chart sheet offers **I destroyed it** later, as a kept Seed
   XOR part's does (it leaves the plan in every open vault that keeps
   it, and the flow's plan while Back up is open). On the board, the old
   set is a group of its own under the set, "SLIP-39 · old set", its
   chips "Old group 1 share 2 · still kept", the chart's line and sheet
   title "Seed 1: Old group 1 share 2 · still kept". Group and share are
   numbered from 1, as everywhere a person reads them. A note on a share
   (checked, marked) follows it when it becomes a kept share, and goes
   when it is destroyed. Whether Back up offers making a new SLIP-39 set
   is not part of this decision.
7. **Rotate the set reaches the key.** Convert's Rotate the set, saved,
   records the new set on the loaded key whose recorded set is the same
   set (point 1) as the one typed in and rotated, in place of it; a
   rotated set no loaded key records is recorded nowhere, as before. The
   plan learns of it the next time Back up opens (point 2). Add a share
   and Replace a lost share record nothing, as before.
8. **Where it is stored.** The kept shares are the plan's only (the plan
   record, `docs/VAULT.md` §7 `faraday.plan.{n}`). The key's
   `faraday.slip39` (binary field 8) keeps one set, the current one; its
   layout does not change. A plan with no kept share writes no
   `slip39old` line and no `slipk` token, so it is the same bytes as
   before. An older Faraday reads a plan with either as a plan it cannot
   read (an unknown line or spot token is refused: `slipk0.5.0.1` is no
   `slip` share it knows), and keeps it as read, named, unused.
9. **Not a security trade-off.** A kept share records its seed, its old
   set's public facts and its place, never a word; no new copy of secret
   data, no new `unsafe`. An old set still kept is counted as the
   exposure it is.
10. The spec is `docs/BACKUP-FLOW.md` §17.26.
