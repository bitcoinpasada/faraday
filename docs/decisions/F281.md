# F281 Timing and memory side channels on the offline device are outside the security model: not looked for, not recorded, not fixed (2026-11-17)

**Kind:** Record
**Status:** Active
**Area:** crypto
**Held by:** repo.security-scope

*Amends F250 (owner, 2026-11-17): its point 6's stack temporaries, timing
and loads indexed by a secret are no longer later work and no longer read
for in review. Points 1 to 5 and 7 hold as written. F181 holds as written.*

**Why.** Until now a side channel on the offline device was later work:
each one found was recorded and was to be fixed when the app was mature.
The record only grew. Rust makes no promise about where a value has
been: a move, a return by value, a spilled register or a library call
can each leave a copy, and no test can show that none remain, so the
count measured how hard the code was read and could not reach zero. Many
of the copies were inside other people's libraries. What the work bought
is small. Timing needs someone measuring the computer while it runs: the
device has no network, runs no other program, and the online side sees
only a code or a file a person carries across. A leftover copy needs
someone reading memory after the secret is done with: while a vault is
open the keys are live in memory anyway, and at every lock the
application restarts and the kernel zeroes freed memory, with no swap
and no core dump (`docs/SECURITY-MODEL.md`).

**Decision** (owner, 2026-11-17).

1. On the stick and the Pi, code whose time depends on a secret, and a
   copy of a secret left in freed memory, on the stack or in a library's
   own buffer, are outside the security model. They are not looked for,
   not reported by a review, not recorded as open work and not fixed.
   The same holds for Faraday Demo and the Starter, which hold test data.
2. Four things stay in scope and are ordinary bugs: a secret still
   reachable in the application's own state after the screen that needed
   it is done, or after a lock; one of Faraday's own secret types that
   does not wipe what it holds; secret-key arithmetic done outside a
   constant-time library; and a comparison that decides access.
3. What bounds a leftover copy is kept and checked as a mechanism: the
   restart at every lock, the kernel's zeroing of freed memory, no swap
   and no core dump, the leak tests of F250 and the fuzzing of what the
   online side sends.
4. A document says no more than this: where wiping does not reach is
   stated as a limit (`docs/KEYS.md`), never as work to come.
