# F265 A push to main whose head commit already passed the check runs nothing again (2026-11-14)

**Kind:** Record
**Status:** Active
**Area:** repository
**Held by:** repo.ci-check

*Amends F183 (2026-11-14): its token may also read the list of workflow runs and caches, in the one first job below; everything else F183 says holds. F212 (caches written only by a push to main) holds unchanged.*

**Why.** The push train checks its tip as `check` started by hand on a
branch, then fast-forwards main to that same commit; the push started the
whole check again on the same commit, about eight minutes with nothing new
to learn.

**Decision** (owner, 2026-11-14).

1. **A first job, `gate`,** runs on a push to main (on nothing else it
   does anything). It asks the API, with the read-only token (`permissions:
   contents: read, actions: read`, on that job only), for a run of `check.yml`
   on the same head commit that ended `success` and is not this run.
   It writes the run it relies on into its log and the run's summary.
2. **A pass found, the rest does nothing,** provided main's cache holds the
   dependencies each job would save for the commit's manifests and
   lock files (the keys of F212 point 4) and the tools cache's key: the
   jobs are skipped and `check` is green. When a manifest or lock file
   changed, so a key is missing, only the fourteen test shards are
   skipped: the other jobs run as before, so main still saves its
   caches (F212 point 2). No pass found: the whole check runs as before.
3. **The result is still one.** `check` passes only when `gate` passed
   and every other job passed or was skipped by `gate`.
4. **A commit, not a tree.** The pass is looked up by head commit, which
   a fast-forward keeps; a rebuilt commit with the same tree runs the
   check. Nothing else changes: pull requests and runs by hand run the whole
   check, uses no secret, and writes nothing.
