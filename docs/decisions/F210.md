# F210 The fuzz run before a release may run on GitHub Actions (2026-11-04)

**Kind:** Record
**Status:** Active
**Area:** repository
**Held by:** repo.ci-check

*Amends F183 (2026-11-04): a second workflow, started by hand, runs the fuzz run; everything else F183 says of what GitHub Actions may do holds for it.*

**Why.** The run before a release takes a computer about an hour: 600
seconds for each of the targets, as many at once as it has cores. On one
computer that is an hour in which nothing else can run on it. GitHub's
runners are free for a public repository and each has four cores, so the
same run, split, can go on beside the rest of a release's work.

**Decision** (owner, 2026-11-04).

1. **A second workflow**, `.github/workflows/fuzz.yml`, started by hand
   on the tree to fuzz (`workflow_dispatch`). It never starts by itself: a
   fuzz run is a release's, not a push's.
2. **The same run.** It runs `tools/fuzz-release.sh` and
   `tools/fuzz-corpus-export.sh` with the time a target that any builder
   would use, from the last published corpus, and joins the parts with
   `tools/fuzz-join.py`. Its record says what ran, and a builder without
   GitHub still runs the whole of it with `just fuzz-release`.
3. **F183's limits hold.** It only reads; it uses no secrets; the checkout
   keeps no credentials; it uses only GitHub's own actions, pinned by
   commit, on GitHub's standard runners. It builds nothing for release:
   the fuzz targets it compiles leave its jobs only for its own other jobs.
   It keeps no build output in a cache.
4. **What comes out** is an artifact: the record, the corpus and any input
   that crashed a target. Publishing the corpus stays outside GitHub
   Actions, after the release.
