# F231 A passphrase record belongs to exactly the key it names: saving another passphrase of one seed asks nothing, and only codex32 shares of one set are grouped (2026-11-09)

**Kind:** Record
**Status:** Active
**Area:** security
**Held by:** keys.vault-contents-never-refuse

*Amends F194 (2026-11-09): point 2's "Related secrets are not damage: several passphrases for one key, and several codex32 shares of one index and key, are each kept and read, and the app labels each (\"1 of 2 passphrases for key {fingerprint}\") and warns when saving one that the vault already holds (Continue / Cancel; built later)." is replaced for passphrases; for codex32 shares it stands.*

**Why.** A passphrase record's `for` is the fingerprint of the key that the
seed's words make together with that passphrase, so two real passphrases of
one seed name two keys, never one. "Several passphrases for one key" could
only be a record made by hand whose `for` its passphrase does not make, or
a fingerprint collision, so the count, the label and the warning only ever
described a damaged record. People who keep several passphrases of one seed
do it on purpose, and a warning every time is noise. Telling the passphrases
of one seed apart by derivation would cost a derivation per pair on the
device for the same little gain.

**Decision** (owner, 2026-11-09; `docs/VAULT.md` §7 and §7.2).

1. A passphrase record belongs to exactly the key its `for` names. Saving
   another passphrase of one seed asks nothing, and the Contents list gives
   no count for passphrases.
2. Where the Load sheet offers several passphrases for one seed, each
   choice is labelled by the key it makes ("Passphrase for key
   {fingerprint}"), with the vault's name when several vaults are open. It
   loads one key at a time.
3. Two records that name one key (made by hand) are each kept and listed
   plainly with nothing shown; Load uses the one that makes the key.
4. Only codex32 shares of one index and key are grouped and counted, and
   saving a share of a set the vault holds still asks first (Continue /
   Cancel), as F194 point 2 says.
