# F297 The Windows programs link with lld and delay-load uxtheme and dwmapi from System32 (2026-11-20)

**Kind:** Record
**Status:** Active
**Area:** starter
**Held by:** build.sh's checks in the Windows build

*Amends the Windows programs' library loading (`docs/STARTER.md` §2): the
load configuration's `DependentLoadFlags` and `SetDefaultDllDirectories`
stay; the linker and two imports change.*

**Why.** On Windows 11 (Procmon) the Starter's `.exe` mapped `propsys.dll`,
`uxtheme.dll` and `dwmapi.dll` from its own folder at process start: its
direct imports that are not KnownDLLs. The load configuration's
`DependentLoadFlags` does not apply to an `.exe`'s own static imports, and
`SetDefaultDllDirectories` in `main` runs after them. A file of that name
in Downloads beside the Starter would run as the person (as administrator
in the elevated copy). Faraday Demo's Windows `.exe` has the same shape.

**Decision** (2026-11-20; `docs/STARTER.md` §2).

1. **propsys.dll** is no import: `sys.rs` loads it with `LoadLibraryExW`
   and `LOAD_LIBRARY_SEARCH_SYSTEM32` where `PSGetPropertyKeyFromName` is
   used, and fails closed if it or the function is missing.
2. **uxtheme.dll and dwmapi.dll** (winit's `SetWindowTheme`,
   `DwmSetWindowAttribute`, `DwmEnableBlurBehindWindow`) are delay-loaded:
   `faraday/shells/window/build.rs` makes their import libraries with
   `llvm-dlltool`, and `build.sh` passes `--delayload` for each. They load
   at first use, after `main`'s `SetDefaultDllDirectories`, so from System32
   only; a missing one stops the program.
3. **The linker is LLD**, the `rust-lld` of the pinned Rust tarball, with
   `llvm` in the container for `llvm-dlltool` and `llvm-readobj`. The
   stack keeps GNU ld's 2 MiB main-thread reserve (`--stack`). LLD points
   the load configuration directory at `_load_config_used` itself, so
   `build.sh` no longer patches the image.
4. **`build.sh` checks** (they fail the build) that no non-KnownDLL library is imported at
   start, that the delay imports are exactly `dwmapi.dll` and
   `uxtheme.dll` with their address tables in a writable section, and (as
   before) the load configuration's size and `DependentLoadFlags`.

**Rejected.**

- GNU ld with `dlltool --output-delaylib`: the delay import address table
  lands in read-only `.idata` and mingw-w64's helper writes it without
  `VirtualProtect`, so the first call faults; and GNU ld leaves the
  delay-import directory empty, so no check could read it.
- LLD with windows-targets' own import library: it delays only short import
  members, so nothing is delayed.
- A winit patch: a fork needs `cargo vet` and a deps page.

LLD's headers differ from GNU ld's (OS and subsystem version 6.0, checksum
0, TERMINAL_SERVER_AWARE set): harmless.
