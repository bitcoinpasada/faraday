# F134 Faraday signs a boot program only when it is a release's own (2026-10-27)

**Kind:** Record
**Status:** Active
**Area:** security

**Why.** Faraday's Secure Boot signing (Vaults → Secure Boot keys →
Sign) signed any EFI image copied in from a stick. A boot file changed
on its way there would have been signed with the person's db key and
then started under their own Secure Boot. Whatever puts a signed boot
file on a stick (Faraday Starter, or a person by hand on a computer),
only a genuine release's boot program should ever carry that signature,
and not an older release's, whose fixed faults the signature would let
back in.

**Decision** (owner, 2026-10-27).

- Before signing an EFI image, Faraday needs the release's `SHA256SUMS`
  and `SHA256SUMS.asc` in the Inbox beside it. The `.asc` must be a
  detached OpenPGP signature over `SHA256SUMS` that verifies with a
  release key built into Faraday (`faraday_sb::release::KEYS`), checked
  by `faraday-pgp` (`verify_detached`). `SHA256SUMS` must name the
  release on its first line (`# Faraday X.Y.Z, commit …`) and list the
  file under the name the release publishes it as,
  `faraday-X.Y.Z-BOOTX64.EFI`, with the file's SHA-256.
- The release must be at least as new as the Faraday signing it (its
  `X.Y.Z` against the running build's, a pre-release counting as its
  release): a genuine older boot program is refused. To sign an older
  release, sign it on that release's Faraday.
- Otherwise the signing page names the refusal in place of the hold,
  the hold signs nothing, and nothing reaches the Outbox: "This file is
  not an EFI image" (a file that does not read as a PE image has no
  SHA-256 taken to compare), "No signed sums from a Faraday release are
  beside this file", "The release's sums are not signed by Faraday's
  release key", "Release X.Y.Z is older than this Faraday (A.B.C); sign
  a release at least as new", "This file is not the boot program of
  release X.Y.Z".
- **Fail closed.** The check is stricter than `gpg --verify`, and a
  release's signing must meet it (GnuPG's `gpg --armor --detach-sign`
  and Faraday's own GPG signing both do):
  - one ASCII-armoured block with its CRC-24 checksum line, right, and
    nothing after its end line; one signature packet in it;
  - a version-4 signature of type 0x00 (binary; a `--textmode` 0x01
    signature is refused), EdDSA on Ed25519, over SHA-256 or SHA-512,
    its creation time in the hashed area, no hashed signature expiry,
    and no critical subpacket but the creation time and the issuer (an
    issuer only names the key to try, so marking it critical changes
    nothing);
  - made by the certificate's signing subkey, inside both keys' life;
  - the certificate exactly one Ed25519 primary key and one Ed25519
    subkey whose newest binding gives it the signing flag (0x02) and no
    other, the binding verified with the primary key and carrying the
    subkey's own primary-key binding (type 0x19, as RFC 9580 requires of
    a signing subkey) verified with the subkey; no revocation in it;
  - in the sums, the boot program's line exactly once, `sha256sum`'s
    two forms (two spaces, or a space and `*`), LF or CRLF line ends.
- The hash listed is the plain SHA-256 of the unsigned file, not the
  Authenticode image hash, so the line is the one `sha256sum -c` checks
  and a person can check what Faraday checks with standard tools. A file
  that already carries a signature does not match; the release's own
  unsigned file is the one to sign.
- The release key built in is `faraday/release-key.asc`, fingerprint
  D1AF A712 ABEF 9010 9A1B 587F F153 6BE0 7E23 4CFD, compiled in with
  that fingerprint, which the certificate must carry. The list may hold
  more than one key: across a rotation it holds the old key and the new
  one, the new key signs from the release that first carries it, and the
  old key leaves the list in a later release. A key is never taken from
  the stick.
- Signing goes only through a checked release: `faraday_sb::release::sign`
  takes a `Release`, which only the check makes, and signs only the
  bytes whose SHA-256 it names. `faraday_sb::pe::sign`, which signs any
  image, exists only under faraday-sb's `sign-any` feature, for its own
  tests and examples and the fuzz target; `tools/lint-keys-tests.sh`
  keeps it out of every shipped binary.
- A release publishes its boot program as `faraday-X.Y.Z-BOOTX64.EFI`,
  the stick image's `EFI/BOOT/BOOTX64.EFI` byte for byte, beside the
  images and listed in `SHA256SUMS` (`faraday/tools/stage-release.sh`,
  which refuses a stick image without one or whose boot program does
  not carry the images' build ID). It is not in the Starter's payload,
  which carries the whole image.
- Faraday's tests and the snapshot tool's sessions also take a test
  release key made by GnuPG (`tools/vectors/release-sums/`), under
  faraday-core's `testkit` feature, which `tools/lint-keys-tests.sh`
  keeps out of every shipped binary.

**By hand.** Download the release's `faraday-X.Y.Z-BOOTX64.EFI`,
`SHA256SUMS` and `SHA256SUMS.asc` onto the stick's data partition, copy
the three in on Faraday, sign the boot program in Vaults → Secure Boot
keys, write the signed file back, and on a computer, once the stick
holds that release, copy it over `EFI/BOOT/BOOTX64.EFI` on its boot
partition (`FARADAYBOOT`) (`README.md`, "With Secure Boot").

**Rejected.** Matching on the Authenticode image hash, which would let
an already-signed file match too: `sha256sum -c` cannot check it, and
the release's file is the one Faraday signs. Taking a key from the
stick, or a fingerprint the person types: the check would then be only
as good as what came in with the file. Signing any genuine release,
older ones included: an old release's boot program, signed, would boot
under the person's key with whatever that release got wrong.
