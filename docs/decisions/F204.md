# F204 SLIP-39's set actions are in Convert a seed; codex32's stay with the backup (2026-11-04)

**Kind:** Record
**Status:** Active
**Area:** keys
**Held by:** review

*Replaces one line of F88 (2026-10-23), for SLIP-39 only: "Set actions
(add, replace, rotate) stay with the backup, for codex32 and SLIP-39
alike."*

**Why.** F88 kept the set actions with the backup because they change
what a plan's places keep. That holds for a codex32 set: a plan and a
vault's key record keep a codex32 set's facts. It does not hold for
SLIP-39: a backup plan has no SLIP-39 form
(`faraday/faraday-plan/`) and a vault's key record keeps nothing
of a SLIP-39 set, so the chart has no such node for the actions to sit
on.

**Decision** (owner, 2026-11-04).

- Add a share, Replace a lost share and Rotate the set for SLIP-39 are
  in Tools › Convert a seed, as a new source, **A SLIP-39 set**: the
  person types enough shares and gets the new shares. Nothing is
  remembered; no vault, plan or backup changes.
- The typed shares are held in `faraday-keys` as a transient value, as
  an aezeed is: never a key of the session, the vault, Explore or Lock
  in; wiped by a forget, by another source and on lock. They leave only
  as the shares the operations make, through `Reveal::PaperForm`.
  `faraday-keys` drops a held set when an aezeed is held and an aezeed
  when a set is held; choosing a loaded key as the source is the screen's
  forget of the set, so "another source" holds for a key only once the
  screen does it.
- No passphrase is taken and none is decrypted: the read-back compares
  the EMS and its parameters, so the set's own passphrase still opens
  the same wallet.
- codex32's set actions stay with the backup, unchanged
  (`docs/CODEX32.md` §9.7). The rest of F88 stands.
- The spec is `docs/SEED-CONVERSION.md` §8.
