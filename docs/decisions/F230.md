# F230 An OpenTimestamps proof is checked on the device against a block header the person gives, checked against python-opentimestamps (2026-11-09)

**Kind:** Record
**Status:** Active, built: the reader, the cross-check against python-opentimestamps and the Check a timestamp tool
**Area:** signing
**Held by:** review

**Why.** An OpenTimestamps proof (`.ots`) shows that a file existed by
the time a Bitcoin block was mined: a list of operations takes the
file's hash to a value the block's merkle root commits to. A person
keeping a file offline (a signed statement, a backup's checklist) can
check its proof without a network, given the block's 80-byte header.
OpenTimestamps is a published format with its own specification and a
reference implementation, python-opentimestamps, and other
implementations read it (JavaScript, Java, Rust); it is a convention
several programs use rather than one project's format alone, and it
enters under STANDARDS §0 as one. Faraday is offline, so it cannot ask
a calendar or a node for anything.

**Decision** (owner, 2026-11-05).

- **A tile in Tools, Messages, Check a timestamp**, beside Check a
  signed message. It takes an `.ots` file and the file it timestamps
  (or that file's hash), both in Files, and a block header the person
  gives: typed or pasted as hex, scanned as a QR code, or a file in
  Files.
- **What is checked.** The proof's magic bytes and version; the file's
  hash under the operation the proof names, against the proof's digest;
  then each path of operations (append, prepend, SHA-256, SHA-1,
  RIPEMD-160, Keccak-256, reverse, hexlify, as the reference reads them)
  down to its attestations. A path ending in a Bitcoin attestation gives
  a value that must equal the given header's merkle root, at the height
  the attestation names. A match shows the block's hash, height and
  time, for the person to compare with a node or explorer they trust;
  Faraday cannot know which header is in the chain, and says only that
  the file is committed to by the header given.
- **Trusted through SHA-256 and RIPEMD-160.** A Bitcoin path counts only
  when the file's hash and every hashing operation on it are SHA-256 or
  RIPEMD-160: a path through SHA-1 or Keccak-256 is shown with that
  operation named and not counted, and the walk goes on to show where it
  reaches. A file taken with SHA-1 is not counted either (Keccak-256 as
  a file's hash is refused). The owner's call (2026-11-10): do what
  EntropyLab does, which works SHA-256 and RIPEMD-160 steps alike and
  stops at a SHA-1 or Keccak-256 step. The OpenTimestamps reference
  counts a path through any of the four, and so Faraday still differs
  for SHA-1 and Keccak-256, which the cross-check lists. RIPEMD-160 sits
  inside the calendars' own tree, so most older proofs pass through it
  and would never count otherwise.
- **Listed and not trusted:** a pending attestation, with its calendar's
  address (the proof is not yet complete, and Faraday cannot upgrade
  it); a Litecoin or Ethereum attestation, and one of a tag Faraday does
  not know, by its tag. A proof whose Bitcoin attestations do not match
  the header given says so for each.
- **Refused, fail closed:** a proof with the wrong magic or a version
  other than 1, trailing bytes, an unknown operation, an operation's
  argument or result over 4,096 bytes, a tree deeper than 256, a
  height that does not fit, and a header that is not 80 bytes or whose
  own proof of work does not meet its stated target.
- **A parser of untrusted input, fuzzed:** the proof's reader and the
  walk of its operations have a fuzz target in `faraday/fuzz`, with the
  reference's own example proofs as seeds.
- **Checked against python-opentimestamps** (F160), pinned and vendored
  under `tools/reference/`: in a cross-check area of its own, its
  example proofs, random proofs and trees built through its own classes,
  each read and verified against headers by both, and proofs with a byte
  changed or cut short, which both refuse, the SHA-1 and Keccak-256 case
  above listed as Faraday's difference.
- **Where it lives:** a crate of its own, `faraday-ots`, that holds no
  secrets; the tile in a `faraday-core` area. A proof's reader and the
  walk are a piece written here: no Rust implementation is established
  (F178), and `written_here` in `tools/lint-crypto.counts` goes up by
  one; SHA-256, SHA-1, RIPEMD-160 and Keccak-256 are libraries Faraday
  already uses or the RustCrypto crates.
- **Faraday makes no timestamps.** Making one needs a calendar online.
- **In Practice** the tile takes a sample proof and its header in
  `faraday-samples`, and the samples table of `docs/MODES.md` §6 lists
  them.
