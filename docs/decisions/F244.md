# F244 Keep data refuses the same build only when the stick's boot partition is already the release's (2026-11-11)

**Kind:** Record
**Status:** Active
**Area:** starter
**Held by:** tests

*Amends F2 (2026-11-11): the same build is refused only when the stick's boot partition is already exactly the release's; everything else F2 says holds.*

**Why.** Replace Faraday, keep data writes the boot partition from its
start. If the write stops part way (the stick is pulled, a read-back
fails, the window is closed), the new build's version string is already
at the start of the partition while the rest is still the old build's, and
the stick no longer starts. Pressing Again then read the stick as "the
same build" and refused keep data, so the only way left was to write the
whole stick, which erases the vaults and settings that keep data was
chosen to keep.

**What it does.** "The same build" means that the build ID on the stick
equals the release's and the stick's boot partition has the SHA-256 the
release's list gives for its `-boot.vfat`. Keep data then refuses it, as
F2 says. A stick whose build ID matches but whose boot partition differs
is written as any other build is, with no warning. A stick whose boot
partition could not be read (the sum is unknown) is not known to hold the
same build, and keep data writes it. The Starter reads the sum from the
stick's boot partition in the shell's worker thread, and the elevated
copy on Windows checks it again before writing. An image with no known
boot-partition sum (a developer's whole image) is never the same build.

**The owner's decision** (owner, 2026-11-11; `docs/STARTER.md` §3.2,
D15): the same build is the stick's boot partition being already exactly
the release's.
